# OS identity for confined agents

## Status and trust boundary

This is the target design for agent-scoped authorization. The current Anthropic launcher uses a loopback TCP bridge with a capability visible to the agent. Its session directory policy hides sibling capabilities when agent file allowances do not overlap the internal session root, but the processes still share one UID. The capability authenticates the bridge to the broker; it does not identify the agent to the operating system. An MCP client name, environment variable, request reason, PID supplied by the client, or readable token must not become a managed principal.

An opt-in transport foundation now exists in `src/peer-identity.ts`. It accepts a Unix socket only after a small native helper reads `getpeereid` on macOS or `SO_PEERCRED` on Linux from the accepted descriptor. The broker process registers one live session per UID, optionally pins the GID, requires a Linux cgroup v2 path, and closes its connected sockets when that registration ends. A stopped UID and session ID cannot be registered again during the same broker process lifetime. Each session is limited to eight open sockets; at most 32 connections may await peer verification. The connection idle deadline defaults to 35 minutes, so the eventual protocol handler must enforce shorter header and request-body deadlines. Session registration is an in-process trusted API; it must never be exposed as an agent request. Build the helper with `npm run build:peer-credentials` when using this adapter. The normal MCP server and Anthropic launcher do not yet use it. No privileged identity launcher, socket provisioning, or supported host network enforcement is installed and connected. The model relay is an opt-in in-process foundation, not a native client transport. This foundation must not be presented as completed confinement.

The broker is an s-gw process outside the agent's confinement. It owns the credential store, approval policy, audit record, and authenticated HTTPS/SSH executors. A trusted launcher starts each agent inside a separate OS security identity, registers that identity with the broker, and controls its lifetime. The broker accepts requests over local IPC, asks the kernel who connected, and maps that identity to exactly one active launcher record. The agent can choose a display name, but policy and reusable grants use the broker's principal and session IDs. A broker process running under the same unrestricted account as an unconfined agent does not provide this boundary.

## Common protocol

1. The trusted operator starts an agent through s-gw. The launcher creates a unique security identity for each concurrent session, a scoped workspace, and a session record. The session ID is not an authentication secret.
2. The launcher drops the agent's privileges and passes only the IPC location and nonsecret configuration. Broker credentials, policy files, private SSH material, and approval authority never enter the agent's filesystem or environment.
3. On each IPC connection the broker obtains the kernel's peer identity. It rejects an unknown identity, one mapped to a different live session, or a connection after the launcher reports the session stopped. It does not accept identity fields in request JSON.
4. The broker binds each request, approval, policy match, reusable permit, execution claim, and execution recheck to the verified principal and session. Knowing a request ID or copying a permit cannot let another agent execute it. The operator's own CLI and approval UI remain separately authorized control-plane paths. The broker revokes outstanding permits and closes in-flight channels when the session ends.
5. The broker performs approved HTTPS/SSH actions itself. Agent network policy prevents direct access to credential-backed service destinations. A separate model transport is required if a native agent must make authenticated model requests without holding its model credential.

The approval console is a separate operator control plane. Its authentication bootstrap must be inaccessible to the agent, including through any loopback web page or local URL. A distinct agent UID alone does not protect a listener shared across identities. The operator UI needs an authenticated native channel or a token delivered only by a trusted opener, and agent egress policy must block its listener. Test this before treating operator-only execution as a trusted path.

The three components have different privileges:

| Component | Runs as | Owns |
| --- | --- | --- |
| Installer/launcher | Root or a narrow privileged service | Agent identity creation, process launch, workspace access, network policy, and cleanup. It never handles credentials or decides approvals. |
| s-gw broker | Operator account or a dedicated service account | Store, policy, approval UI, audit log, and approved execution. IPC input alone never authorizes a command. |
| Agent | Unique unprivileged identity for the live session | Its permitted workspace and an IPC client. It receives no broker key, operator session, or reusable authorization bearer. |

The launcher registers `{session ID, OS identity, workspace, start time}` through a control channel authenticated separately from the agent IPC. The broker records this before accepting agent requests. On each connection it obtains the peer identity from the kernel and looks up exactly one live session. The request is rejected if registration is absent, ambiguous, ended, or inconsistent with the connection. The broker stores the verified principal and session on the request itself, and checks them again when a permit is consumed and immediately before execution. The agent may know its UID, SID, or session ID; security comes from its inability to make the kernel attest to another identity at the broker connection. The session ID and IPC path are routing information, not credentials. Keep one live session per OS identity; do not recycle the identity until every old process and connection is gone and its grants are revoked. The in-memory UID quarantine prevents reuse only until the broker restarts. A trusted launcher must verify the process and socket teardown across broker restarts before any UID is assigned again.

Protect the launcher's control channel separately: only the operator's broker may register, change, or stop a session, and the launcher accepts a fixed launch plan rather than arbitrary privileged commands. A root helper that checks only the operator UID also trusts every other process under that UID; if same-user processes are in scope, attest the packaged broker's code identity and the control channel's peer before accepting a launch plan. Keep the broker executable, store, socket directory, and served operator UI assets outside every agent-writable path. Give each agent access to only its own internal launch manifest. A `0700` directory does not separate two processes with the same UID; the current same-UID launcher needs explicit cross-session file denial until distinct identities are available.

The agent cannot be allowed to launch a new privileged helper, inherit the broker's file descriptors, write the broker executable or store, or reach credential-backed services directly. The launcher supplies a fresh allowlisted environment and closes unexpected inherited handles. It must establish broker IPC only after dropping to the agent identity: Unix peer credentials are captured when a socket connects, so a privileged preconnected descriptor would carry the wrong identity. A writable workspace is never a trusted source of policy, commands to execute as the broker, or TLS/SSH verification settings. Other local IPC routes matter too: audit host Unix sockets, macOS Mach/XPC services, and Windows named pipes/COM endpoints for paths into operator authority. If the native model client needs credentials, a broker-owned model relay must be evaluated separately: the client intentionally connects to that relay, and the broker opens its own authenticated TLS connection upstream. The relay must accept only fixed provider endpoints and methods, remove any agent-supplied credential header, and never offer arbitrary URLs or `CONNECT`. This does not require intercepting the agent's arbitrary TLS traffic.

An API-funded Claude Code or Codex model session may be able to use such a relay through the clients' custom gateway settings, but it needs a separate streaming implementation; the existing owned HTTPS action buffers its response. The clients' existing subscription sign-ins must not be treated as broker-owned credentials: the documented gateway paths can still send a client-held login token. An API-key or separately authorized OAuth relay may change billing, model availability, or client features and requires native acceptance before it can replace any existing sign-in workflow.

## macOS

For a host-native agent on macOS 13 or later, install a signed, narrow LaunchDaemon/helper through ServiceManagement with the required administrator approval. Provision a pool of dedicated unprivileged local accounts during installation, then assign one account to each concurrent session; recycling an account requires closing its old sockets and revoking its grants first. The helper only accepts a vetted launch plan from the operator's s-gw process, prepares a session workspace, drops supplementary groups and UID/GID, and starts the agent. It must not become a general command runner. It closes inherited network and broker descriptors and creates no Internet socket before dropping UID. The s-gw broker can remain a LaunchAgent in the operator's login session so it can use the operator's authorized Keychain context. Its store stays readable only by that account.

An additive runner scaffold is in `native/macos-agent-launcher/uid-runner.c`. It is not installed, wired to the CLI, or usable from an ordinary process. It requires real and effective root, an accepted Unix control socket on fd 3 whose peer is the broker account, and a separate root-owned network-policy service socket on fd 4 that answers `READY-V1` for the exact UID and session. Neither socket service exists in the current product. The runner requires a dedicated `_sgwagent_` account, a private root-owned UID lease directory, a staged root-parented workspace, and a broker-owned Unix socket. It records a nonreusable UID tombstone before fork, drops supplementary groups and UID/GID, changes to the agent workspace, closes every inherited descriptor above standard I/O, and requires the broker to acknowledge the UID/session after the agent identity connects. The future broker must actually verify that peer before acknowledging. It redirects standard streams to `/dev/null`; a trusted PTY bridge is needed for interactive agents. The network-policy service must attest to a supported, effective egress boundary before answering; no such service or attestation exists. The runner's process-group cleanup is best effort because a child can create a new session. The installer must enumerate and terminate all processes under the agent UID before ever retiring that account.

`src/macos-agent-session.ts` provides a broker-owned, exclusive on-disk UID lease before registration with the verified Unix peer server. The UID tombstone remains even if registration fails or the broker restarts, so an old account is not silently reassigned. The lease directory must be created outside every agent-visible tree with broker-only access. A fresh account is required for another session unless a separate privileged teardown and recovery workflow is built and reviewed. Current unit tests use the broker account and synthetic UIDs; they verify lease persistence and fail-closed validation, not isolation between two real macOS accounts.

The optional `acknowledgeMacAgentLaunch` handler in `src/macos-agent-probe.ts` can be used as the `onConnection` callback of the verified Unix peer server for the runner's one-shot launch probe. The runner half-closes its write side after `HELLO-V1 <kernel UID> <registered session ID>\n`. The handler requires that exact frame followed by EOF within 1.5 seconds, sends the matching `READY-V1` only after the native `getpeereid` adapter has registered that peer, and closes the probe connection. Delayed extra bytes and a complete frame without EOF are denied. The claimed UID and session text never create or change a principal. This handler is not connected to the CLI or a working agent request protocol. Its real-socket tests use the current user as a synthetic agent identity; two provisioned UIDs and an installed root runner are still needed to prove the boundary.

Before installed use, the root and broker lease records must be coordinated with an atomic launch record. Inspect effective macOS ACLs as the provisioned agent UID: owner/mode checks alone do not prove that the agent cannot read or write a broker path. Test UID-wide teardown, retained network denial, and the broker handshake with two real accounts; the present tests do not cover these boundaries.

For each concurrent session, use a distinct agent UID. Grant that UID access only to the selected workspace and its broker Unix socket; deny the operator home, Keychain, other session directories, and direct network egress. A repository inside a `0700` operator home cannot simply be opened by another UID. Stage a scoped checkout outside that home under a launcher-controlled directory, or use an audited access mechanism that exposes only that checkout; changing the home directory to world-traversable would expose other known paths. Put the socket under a broker-controlled directory that the agent can traverse but cannot replace. On the accepted socket the broker calls `getpeereid`, maps the returned effective UID to its live launcher record, and rejects anything else. XPC audit tokens and code-signing requirements can add checks for the packaged helper, but signing identifies an executable, not arbitrary agent code running inside it. A plain Seatbelt sandbox under the operator's UID is not a distinct principal.

The accepted socket keeps the identity of its original connector. If an agent can pass that file descriptor through a shared Unix socket to another UID, the receiver can use the first agent's grant. Keep each agent's IPC endpoints and writable socket paths separate, block cross-agent descriptor passing, and include a deliberate `SCM_RIGHTS` transfer attempt in native acceptance.

For host-native CLI agents, Apple's supported path for a product that blocks socket flows is a Network Extension content-filter system extension. A `NEFilterDataProvider` can decide whether to allow or drop new flows; `filterSockets` must be enabled, and source process/app audit tokens can help classify the agent. `sourceProcessAuditToken` is nullable and available on macOS 13 or later; a system process may connect on an app's behalf, so source process and source app can differ. Treat an absent or ambiguous token as unclassified, never as permission. The extension must use the appropriate Developer ID entitlement and be installed and enabled before the launcher releases an agent. Do not treat a binary signing identifier or a claimed PID as the agent principal. Only a flow actually delivered to and dropped by the effective provider is denied; the broker's `getpeereid` check separately supplies IPC identity. Apple's deployment technote lists macOS content-filter system extensions from macOS 10.15 and supports Developer ID distribution. Entitlement, provisioning, notarization, extension activation, and filter configuration still need to be verified for the shipped build. Provider behavior after a crash, removal, sleep/wake, and system update, and its coverage of loopback and non-socket traffic, remain native acceptance gates. The product must not launch a confined agent if any required denial cannot be proved active.

Apple explicitly says Packet Filter is not an API for a widely distributed product and directs socket blockers to Network Extension. PF anchors and deprecated `sandbox-exec` profiles are unsuitable as s-gw's shipped enforcement guarantee. Apple also says its new URL filter does not automatically cover applications outside WebKit and URLSession, so it cannot enforce this boundary for arbitrary native agents. A signed App Sandbox without the `com.apple.security.network.client` entitlement is another host-native candidate. One disposable probe on macOS 27.0.1 denied IPv4 and IPv6 loopback TCP for the sandboxed executable and an unsigned child, while an entitled control connected; a temporary Unix socket was also denied. This does not establish native agent compatibility or a usable broker IPC route. A sandbox-compatible IPC path, child behavior, and effective isolation with the actual packaged agent need acceptance before relying on it.

For the stronger macOS option, run each untrusted agent in its own Linux VM using Apple's Virtualization framework. Set `networkDevices = []`, verify the live VM exposes no network device, and expose only a dedicated virtio socket endpoint to a host broker bridge; give the guest a scoped workspace and no host credential or broker-store mount. The host launcher assigns the VM/session identity from its own live VM object, not a field supplied by the guest. The bridge forwards a restricted request protocol to s-gw, which still decides approvals and owns TLS/SSH execution. Host-side broker and operator UI paths remain outside the VM. This changes native macOS agent behavior and file access, so it is an opt-in design until compatibility and user approval support a migration. A VM without a network device still needs acceptance tests for every other host channel: shared directories, clipboard, serial/virtio devices, host services exposed by the bridge, and cross-VM forwarding.

For either host-native or VM mode, the launcher must fail closed if it cannot verify the isolation plan. Probe direct IPv4, IPv6, DNS, UDP, host loopback, and access to the operator console and other agents' IPC paths; guest-local loopback may remain available for agent tools. Verify that broker IPC still works and no connected network descriptor was inherited. For host-native mode, additionally test extension disable/crash/restart, UID-specific filtering, `SCM_RIGHTS` descriptor transfer, host Mach/XPC routes, and two real agent accounts. These tests have not run.

Host-native mode needs privileged installation; VM mode needs the Virtualization entitlement and a managed guest lifecycle. Both need agent compatibility tests. Existing editor processes cannot be retroactively moved to a different UID or VM. Access to files under the operator's home must be granted deliberately, and native agent login will need a broker-owned model transport or another supported sign-in path.

## Linux

Run each concurrent agent in a system-managed unit with a distinct UID. For a writable checkout bind-mounted from elsewhere, provision a dedicated UID for that session. Alternatively, use a uniquely named system service with `DynamicUser=yes` and stage the checkout inside a systemd-managed `StateDirectory=` or `RuntimeDirectory=`; systemd explicitly warns against `BindPaths=` with `DynamicUser=` because later UID reuse could expose persistent files. A system-managed transient unit can set `PrivateNetwork=yes`, `ProtectSystem=strict`, `NoNewPrivileges=yes`, an empty `CapabilityBoundingSet=`, `PrivateDevices=yes`, and restricted namespaces and address families. Use `ProtectHome=yes` when no path beneath `/home` must be exposed. If a provisioned-UID unit needs a selected checkout from `/home`, stage it elsewhere or use `ProtectHome=tmpfs` with an explicit bind; `ProtectHome=yes` cannot be reopened with a nested bind. The private network namespace has loopback for an agent-local forwarder but no direct service egress. `PrivateNetwork=yes` does not hide filesystem Unix sockets: give the unit a private view of `/run` and `/tmp` and expose only its broker socket. Test that it cannot reach host D-Bus, Docker/Podman, SSH-agent, or proxy sockets. The broker stays in the host/user service outside that unit and keeps the store private. Run this as a system unit, or verify the host's user-service namespace support; several isolation settings do not work in every unprivileged user-service configuration.

For an accepted Unix socket the broker reads `SO_PEERCRED` (PID, UID, GID), checks the host UID and the launcher's active unit/cgroup record, and binds it to a session. Create the socket under a broker-owned `/run/s-gw/` path; grant the agent only connect/traverse rights, not directory write rights. A socket under the operator's `0700` runtime directory will not be reachable by the distinct UID. Keep each connection tied to the active unit and close it before the UID can be recycled; a dynamic UID alone must never authorize a durable grant. Do not rely on a user namespace that maps the agent back to the operator's host UID as the sole identity boundary. Terminate the full service cgroup and verify no process remains under the session UID before reuse.

The additive Linux source foundation is `src/linux-agent-unit.ts` and `src/linux-agent-session.ts`. It reserves a static UID and GID in a broker-private, persistent lease directory before starting a unit; neither identity is automatically recycled. Its fixed systemd plan uses a distinct system service, a dedicated root-owned `RootDirectory` under `/var/lib/s-gw/agent-roots/<session>`, a private `/workspace`, `PrivateNetwork`, `PrivateIPC`, private temporary directories, no capabilities or privilege gain, namespace restrictions, and whole-cgroup termination. The only host socket explicitly mounted into the root is the broker socket under `/run/s-gw/agents/<session>/broker.sock`. A root-only manager checks the staged root, executable, and socket ownership before `systemd-run`; it also checks the account database for unintended supplementary groups, since systemd can initialize groups from NSS even when `SupplementaryGroups=` is empty. It reads back the requested unit properties and checks the live main process's UID/GID and supplementary groups, cgroup, chroot, network/IPC/mount namespaces, capabilities, `NoNewPrivs`, and seccomp state. On stop the broker registration is revoked first; the privileged manager stops the full unit and checks for remaining processes under its UID. Existing launch behavior is unchanged.

This is source-only and opt-in. The operator broker cannot call the root-only `SystemdRunAgentUnitManager` directly. A narrow privileged system service, its authenticated control channel to the operator broker, account and root-directory provisioning, a real broker socket mount, and native Linux acceptance are still required. The current code does not install a service or wire a native agent to it. A successful `systemctl show` readback alone does not prove that the host kernel enforced every namespace or mount rule; acceptance must inspect the agent's actual network and mount namespaces and try direct IPv4/IPv6, host Unix/abstract sockets, D-Bus, Docker/Podman, SSH-agent, proxy sockets, and cross-session `SCM_RIGHTS`. The root-owned directory chain and nonwritable socket parent prevent the agent UID from replacing the broker socket, but another process with the broker UID can still race the path check and bind mount. A root-owned socket directory with a broker listener passed by descriptor would close that installation-time race. The profile also needs a trusted PTY/forwarder and a staged native-client runtime before it can support interactive agents. Keep this profile disabled until two real Linux UIDs, the root control channel, revocation, and native-client behavior have passed on each supported kernel and architecture.
Set `launchGate: true` in the source-only plan to hold the agent executable until live attestation and broker registration finish. Stage a root-owned gate binary from `native/linux-agent-gate/launch-gate.c` at `/usr/libexec/s-gw/agent-launch-gate` inside the unit root, with root-owned nonwritable parent directories and an empty root-owned `/run/s-gw/launch-gate` destination. Provision the root-owned `/run/s-gw/launch-gates` host directory. A static Linux build avoids runtime library dependencies inside the chroot; for example, build it on the target architecture with `cc -static -O2 -std=c11 -Wall -Wextra -Werror native/linux-agent-gate/launch-gate.c -o agent-launch-gate`. The root-only manager creates a fresh session directory and `WAIT` marker, bind-mounts that directory read-only into the unit, and starts the gate instead of the agent. It rejects any live process already using the assigned UID. It checks the running gate's actual UID, groups, cgroup, chroot, namespaces, capabilities, command line, gate-binary inode, and read-only release mount. After the broker registers that verified cgroup, the manager rechecks it and atomically publishes a root-owned `GO` marker bound to that unit's `InvocationID` and main PID. The gate rejects a stale marker and times out after 60 seconds without release. Registration or release failure revokes the broker peer and stops the unit. After a confirmed stop with no process under the UID, the manager verifies the marker and directory inodes before cleanup. The broker's persistent lease prevents reuse of that session ID or UID even after cleanup. The ordinary plan remains unchanged.

This gate is not installed or wired to a privileged system service. It has a compile-and-run protocol test, but no native Linux systemd acceptance yet; that test cannot prove systemd's mount or UID enforcement. The gate disables same-UID ptrace before waiting, so the root manager must retain permission to inspect its protected `/proc` links, such as `CAP_SYS_PTRACE`; a manager without that permission fails closed. A root-owned release path and exact `InvocationID`/PID protect against an agent-UID self-release only when the staged root, mount, and system unit pass the live checks above. The operator broker still needs a narrow authenticated channel to the root manager, and the existing source-only path must not be advertised as deployed confinement.

The ordinary live adapter reads a numeric peer PID and then checks `/proc/<pid>/cgroup` in a separate step. PID reuse can make that lookup describe another process, and a connected socket can be passed to a different process. Treat that adapter's cgroup lookup as a guard on top of the unique UID and trusted launcher, not as independent proof of the current socket holder. The opt-in model relay requires the Linux verifier in `src/linux-peer-identity.ts` and `native/linux-peer-identity/verify.c`. It uses `SO_PEERPIDFD`, checks the stable peer process is live before and after reading its cgroup, and fails closed if the kernel lacks that socket option. Build it with `npm run build:linux-peer-identity`. The verifier still identifies the process that connected, not a later holder of a passed socket. The launcher must prevent cross-boundary descriptor passing and cgroup migration before cgroup membership becomes an authorization boundary.

If a native model client only speaks HTTP, an agent-local forwarder can connect to the broker over the authenticated Unix socket. Its TCP listener must be isolated inside that session's network namespace. The broker makes upstream TLS connections and authorizes requests based on the forwarder's verified Unix peer, not a token sent over HTTP.

## Windows

Prefer a distinct AppContainer SID for each concurrent agent session. Create a session profile with `CreateAppContainerProfile` and launch the agent using `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES`; a less-privileged AppContainer additionally needs `PROC_THREAD_ATTRIBUTE_ALL_APPLICATION_PACKAGES_POLICY` with `PROCESS_CREATION_ALL_APPLICATION_PACKAGES_OPT_OUT`, if the CLI supports that environment. Ordinary AppContainers may retain access through `ALL APPLICATION PACKAGES` ACL entries; test effective access to the store, helper and its parent directories, console assets, and IPC objects under the actual package token. Create the process suspended, place it in a Job Object with kill-on-close and no breakaway, install and verify IPv4/IPv6 Windows Filtering Platform rules tied to `FWPM_CONDITION_ALE_PACKAGE_ID`, then resume it. The launcher must terminate or hold the agent if the Base Filtering Engine stops or a required rule disappears. The Job Object controls lifetime but is not the authorization identity. The broker runs at normal full trust outside the AppContainer and keeps its store and credential access under the operator account. If a CLI cannot run correctly in AppContainer, use a dedicated local account for the session with equivalent ACL and network restrictions using `FWPM_CONDITION_ALE_USER_ID`; this requires a privileged setup path.

Expose a local named pipe with an explicit security descriptor granting only the intended agent SID and broker identity; use `PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE`, and the `\\.\pipe\LOCAL\<name>` namespace where required. Do not grant the client pipe-instance creation rights. After reading a request, the server calls `ImpersonateNamedPipeClient`, opens the client token, inspects its account or AppContainer SID and logon session, and matches it to an active launcher record. It checks impersonation success and level before processing and always calls `RevertToSelf`. `GetNamedPipeClientProcessId` is useful for diagnostics but is not the authorization identity. Do not use the default named-pipe ACL, which grants broader read access.

An opt-in, one-request pipe foundation is in `src/windows-agent-pipe.ts` and `native/windows-peer-identity/one-shot.c`. The broker registers a launcher-attested user SID, optional AppContainer package SID, logon LUID, Windows session number, and nonsecret session ID. It burns each SID and session ID for that broker process, limits the session to eight pending exchanges, and requests helper termination on revocation. Each helper creates an unpredictable `\\.\pipe\LOCAL\s-gw-...` name with `FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS`, one message-mode instance, an explicit protected DACL, and a low-integrity label. Client ACEs grant data read/write and no `FILE_CREATE_PIPE_INSTANCE` bit. For AppContainer clients, both the user and package SID have those data rights. A client must request those specific rights; a generic-write open requests instance-creation rights and should fail. The helper reads one bounded message (32 KiB), impersonates the sender of that message, checks the impersonation level, token user SID, AppContainer SID and status, logon LUID, and Windows session number, and reverts before passing the request bytes to the broker process. The broker callback receives a principal derived from the registered SID, never a client-provided name. A response is returned over the same pipe. Build the helper on a Windows MSVC host with `node scripts/build-windows-peer-identity.mjs`.

This code is not installed or connected to the ordinary MCP server, model relay, console, or a Windows agent launcher. The TypeScript wrapper requires an installer-pinned helper hash and invokes the read-only ACL and hash check in `src/windows-peer-helper-acl.ts` on every attempted native opening. It still refuses the native launch until the agent launcher and network boundary are verified on Windows. The inspector checks each existing path component and its raw ACEs, but it is not an `AccessCheck` against the actual agent token and has not run on Windows. Path spelling alone cannot prove the ACL property. Only an injected synthetic helper in isolated tests can run today. The helper uses blocking I/O inside a disposable child process; the broker wrapper applies a deadline and terminates that child, rather than relying on `CancelIoEx` to free an in-use buffer. Revocation also aborts the broker callback's signal, but the eventual handler must honor that signal and recheck policy immediately before any credential-backed execution. Native Windows acceptance must prove the child actually exits on deadline and revocation, the AppContainer dual-principal and low-integrity checks behave as expected, the pipe rejects remote clients and instance creation, and two distinct agents cannot impersonate one another. The launcher still needs AppContainer or dedicated-account creation, a Job Object, WFP rules, persistent SID reuse prevention across broker restarts, and a client that opens the pipe with the exact rights above. Until those pieces and native tests exist, this foundation does not establish Windows confinement or close a bypass in the default product.

An agent-local HTTP forwarder may be needed for stock model clients; it must use the named pipe for broker requests. AppContainer loopback is normally blocked. If native client compatibility requires a loopback exemption, pair it with a WFP rule that allows only that session's relay address and port; a broad exemption would expose other host-local listeners. Windows named-pipe/AppContainer support and CLI compatibility need native Windows acceptance testing.

## Acceptance and rollout

Use synthetic credentials and two concurrent agents with different OS identities. Prove that each can request its own approved action, cannot claim the other's principal by changing MCP names/environment/request fields, cannot connect as the other identity, cannot read the broker store or the other's private files, and cannot reach protected services directly. Kill a session during a reusable action and prove revocation. Test real native model sessions and owned HTTPS/SSH under the same profile on macOS, Linux, and Windows before enabling it by default.

For host-native macOS, first install the two root-owned socket services and an effective, supported network-denial provider, then run the native runner with two provisioned `_sgwagent_` accounts. Verify that `getpeereid` reports each separate UID, not just a synthetic UID registered by the broker's own account. Deny direct connections from each account across IPv4, IPv6, loopback, and UDP, including after the provider is disabled or crashes; a failure to prove denial blocks launch. Kill the runner and a descendant that has called `setsid`, and verify that the broker rejects its old UID after restart and the installer refuses account reuse while any process remains. For VM mode, verify that the guest has no network interface and cannot reach the host except through its own restricted virtio socket; an agent inside one VM must not borrow another VM's session. Test the future PTY bridge and native client startup separately; the current runner deliberately has no interactive stdio.

Add an explicit malicious-peer test: Agent A attempts to read Agent B's launch manifest, borrow its IPC handle, reach B's broker endpoint through every available proxy, and load the operator console on each local listener. The expected result is denial before a credential-backed request is created. Repeat with an ordinary local service intentionally allowed to A, so the test detects accidental loss of that existing access.

Ordinary MCP name-based approvals and the current same-user Anthropic launcher remain compatibility paths until a separate, explicit migration is approved. A partial peer-credential helper added to the current same-UID launcher would not establish managed-agent identity.
