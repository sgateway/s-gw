# OS identity for confined agents

## Status and trust boundary

This is the target design for agent-scoped authorization. The current Anthropic launcher uses a loopback TCP bridge with a capability visible to the agent. Its session directory policy hides sibling capabilities when agent file allowances do not overlap the internal session root, but the processes still share one UID. The capability authenticates the bridge to the broker; it does not identify the agent to the operating system. An MCP client name, environment variable, request reason, PID supplied by the client, or readable token must not become a managed principal.

An opt-in transport foundation now exists in `src/peer-identity.ts`. It accepts a Unix socket only after a small native helper reads `getpeereid` on macOS or `SO_PEERCRED` on Linux from the accepted descriptor. The broker process registers one live session per UID, optionally pins the GID, requires a Linux cgroup v2 path, and closes its connected sockets when that registration ends. A stopped UID and session ID cannot be registered again during the same broker process lifetime. Each session is limited to eight open sockets; at most 32 connections may await peer verification. The connection idle deadline defaults to 35 minutes, so protocol handlers must enforce their own bounds on requests. Session registration is an in-process trusted API; it must never be exposed as an agent request. Build the helper with `npm run build:peer-credentials` when using this adapter. The ordinary MCP server and Anthropic launcher do not yet use it. Linux source now combines root-managed MCP and model relay with two activated sockets, but no privileged launcher, socket provisioning, or supported host network enforcement is installed. Synthetic native Claude Code and Codex tests use disposable stores and a same-UID HTTP bridge to that relay; no production native client is routed through it. This foundation must not be presented as completed confinement.

`src/verified-mcp-server.ts` now provides an optional broker-side MCP listener on that verified Unix peer transport. A trusted caller supplies the broker-owned store and registers a launcher-attested session through its in-process API. `s-gw-mcp-peer-bridge <absolute socket path>` forwards an agent's ordinary MCP stdio stream to that listener after the agent has dropped to its dedicated UID. The bridge knows a socket path, not an authorization secret; the broker uses the kernel peer, registered UID/GID, and on Linux a live pidfd/cgroup check. Each connection gets its own `managedPrincipal` context. This endpoint exposes handle metadata, managed SSH route metadata, owned HTTPS requests, SSH requests limited to operator-managed routes, and execution of approved owned HTTPS/SSH requests. It omits scans, arbitrary broker-side upload source paths, and environment-command execution. The existing stdio MCP server and its tools are unchanged. No production launcher or service registers sessions or configures an agent to use this endpoint yet.

The verified listener admits at most four concurrent tools per registered session, with a 1 MiB MCP frame limit. Session stop closes its sockets. Request creation and execution claims recheck session liveness inside the store mutation, after any lock wait. The connection's abort signal cancels an in-flight owned HTTPS request and kills an owned SSH process tree; source tests cover both and the stdio bridge. These checks prevent a queued request from starting after revocation, but cannot undo a remote side effect already sent before the session stopped. Hosted Ubuntu CI has passed the two-real-UID/cgroup component fixture and the separate managed systemd MCP, broker-owned HTTPS, and teardown fixture. The combined MCP/model-relay fixture also passed in hosted Ubuntu CI with two real agent UIDs, including cross-session model descriptor handoff denial, strict payload rejection, broker-owned synthetic TLS streaming, redaction, cancellation, and teardown. No production launcher or network policy ships here. A transferred descriptor's holder can read replies that were already sent even if per-message checks block its writes. This listener is a transport foundation, not proof that agents cannot bypass s-gw.

The broker is an s-gw process outside the agent's confinement. It owns the credential store, approval policy, audit record, and authenticated HTTPS/SSH executors. A trusted launcher starts each agent inside a separate OS security identity, registers that identity with the broker, and controls its lifetime. The broker accepts requests over local IPC, asks the kernel who connected, and maps that identity to exactly one active launcher record. The agent can choose a display name, but policy and reusable grants use the broker's principal and session IDs. A broker process running under the same unrestricted account as an unconfined agent does not provide this boundary.

Automatic approval now requires a verified agent by default, including when an older store has no verified-only setting or explicitly stores `false`. A name, MCP client metadata, environment hint, process name, or request reason cannot trigger an allow policy or reusable grant. Ordinary clients can still submit requests and receive one-time manual approval; `--allow-unverified-agent` and API attempts to set the option to `false` are rejected. Deny policies remain effective, and requests without an eligible allow or grant stay pending. A verified peer can use a policy matched by principal ID or an eligible grant. To migrate an unattended rule, launch the agent behind a verified OS peer, then create a principal-scoped allow rule or approve a reusable grant for that peer. Unattended HTTPS also requires an exact action key, which binds the method, full URL, headers, body, authentication mode, and timeout. Existing broad HTTPS allow rules stay stored but no longer autoapprove HTTP; these requests need manual approval until an action-specific rule is created from a verified request. A deny policy added after manual approval now blocks that request at execution claim, including environment commands and legacy target SSH. Restoring name-based automatic approval requires reverting this change in a compatible broker deployment after stopping all store writers; the removed flag is not a runtime rollback. This setting is only effective for writers that enforce it: an older or incompatible process writing the same store can bypass or erase it. The store, recovery files, and settings API must be inaccessible to the agent, and every store writer must run compatible code before this can be relied on as a boundary. It does not confine the current ordinary MCP server or make its claimed client name trustworthy.

An ordinary MCP connection may still submit owned HTTPS, SSH, and environment-command requests for manual approval, but its name-only connection cannot claim any approved request. An agent claim requires the same verified principal and nonempty live session ID recorded on the request. The check occurs atomically before the request enters `executing`; a denied claim leaves the approval intact for the operator CLI/UI. A verified agent cannot take over a request submitted by an ordinary client. Migrate owned HTTPS and managed SSH requests to the verified endpoint, or have the operator execute an approved request and share only its sanitized result. The verified endpoint does not currently offer environment commands or target-based SSH, so those ordinary MCP requests require operator execution until a safe verified workflow exists. The ordinary same-UID Anthropic launcher still exposes only a claimed-name MCP client. Rolling back the claim checks requires a compatible broker and a coordinated stop of all store writers with paired home and recovery snapshots; it knowingly restores request-ID claiming by ordinary clients.

## Common protocol

1. The trusted operator starts an agent through s-gw. The launcher creates a unique security identity for each concurrent session, a scoped workspace, and a session record. The session ID is not an authentication secret.
2. The launcher drops the agent's privileges and passes only the IPC location and nonsecret configuration. Broker credentials, policy files, private SSH material, and approval authority never enter the agent's filesystem or environment.
3. On each IPC connection the broker obtains the kernel's peer identity. It rejects an unknown identity, one mapped to a different live session, or a connection after the launcher reports the session stopped. It does not accept identity fields in request JSON.
4. The broker binds each request, approval, policy match, reusable permit, execution claim, and execution recheck to the verified principal and session. Knowing a request ID or copying a permit cannot let another agent execute it. The operator's own CLI and approval UI remain separately authorized control-plane paths. The broker revokes outstanding permits and closes in-flight channels when the session ends.
5. The broker performs approved HTTPS/SSH actions itself. Agent network policy prevents direct access to credential-backed service destinations. A separate model transport is required if a native agent must make authenticated model requests without holding its model credential.

The approval console is a separate operator control plane. Its authentication bootstrap must be inaccessible to the agent, including through any loopback web page or local URL. A distinct agent UID alone does not protect a listener shared across identities. The operator UI needs an authenticated native channel or a token delivered only by a trusted opener, and agent egress policy must block its listener. Test this before treating operator-only execution as a trusted path. A disposable two-listener test confirmed that an ordinary URL-token console sharing the store can still approve and execute a request while a protected console is running. Every listener and writer for one store must enforce the operator boundary before that store is protected.

The three components have different privileges:

| Component | Runs as | Owns |
| --- | --- | --- |
| Installer/launcher | Root or a narrow privileged service | Agent identity creation, process launch, workspace access, network policy, and cleanup. It never handles credentials or decides approvals. |
| s-gw broker | Operator account or a dedicated service account | Store, policy, approval UI, audit log, and approved execution. IPC input alone never authorizes a command. |
| Agent | Unique unprivileged identity for the live session | Its permitted workspace and an IPC client. It receives no broker key, operator session, or reusable authorization bearer. |

The launcher registers `{session ID, OS identity, workspace, start time}` through a control channel authenticated separately from the agent IPC. The broker records this before accepting agent requests. On each connection it obtains the peer identity from the kernel and looks up exactly one live session. The request is rejected if registration is absent, ambiguous, ended, or inconsistent with the connection. The broker stores the verified principal and session on the request itself, and checks them again when a permit is consumed and immediately before execution. The agent may know its UID, SID, or session ID; security comes from its inability to make the kernel attest to another identity at the broker connection. The session ID and IPC path are routing information, not credentials. Keep one live session per OS identity; do not recycle the identity until every old process and connection is gone and its grants are revoked. The in-memory UID quarantine prevents reuse only until the broker restarts. A trusted launcher must verify the process and socket teardown across broker restarts before any UID is assigned again.

Protect the launcher's control channel separately: only the operator's broker may register, change, or stop a session, and the launcher accepts a fixed launch plan rather than arbitrary privileged commands. A root helper that checks only the operator UID also trusts every other process under that UID; if same-user processes are in scope, attest the packaged broker's code identity and the control channel's peer before accepting a launch plan. Keep the broker executable, store, socket directory, and served operator UI assets outside every agent-writable path. The protected browser verifies a broker-signed copy of the UI, but the broker signs bytes read from its local UI directory. A disposable test confirmed that a same-UID edit made before sign-in receives a valid signature and CSP script nonce. Give each agent access to only its own internal launch manifest. A `0700` directory does not separate two processes with the same UID; the current same-UID launcher needs explicit cross-session file denial until distinct identities are available.

The agent cannot be allowed to launch a new privileged helper, inherit the broker's file descriptors, write the broker executable or store, or reach credential-backed services directly. The launcher supplies a fresh allowlisted environment and closes unexpected inherited handles. It must establish broker IPC only after dropping to the agent identity: Unix peer credentials are captured when a socket connects, so a privileged preconnected descriptor would carry the wrong identity. A writable workspace is never a trusted source of policy, commands to execute as the broker, or TLS/SSH verification settings. Other local IPC routes matter too: audit host Unix sockets, macOS Mach/XPC services, and Windows named pipes/COM endpoints for paths into operator authority. If the native model client needs credentials, a broker-owned model relay must be evaluated separately: the client intentionally connects to that relay, and the broker opens its own authenticated TLS connection upstream. The relay must accept only fixed provider endpoints and methods, remove any agent-supplied credential header, and never offer arbitrary URLs or `CONNECT`. This does not require intercepting the agent's arbitrary TLS traffic.

Fixed upstream endpoints alone do not constrain the provider's own tools: [OpenAI remote MCP](https://developers.openai.com/api/docs/guides/tools-connectors-mcp) and [Anthropic's MCP connector](https://platform.claude.com/docs/en/agents-and-tools/mcp-connector) can contact a URL named inside a model request. An opt-in model relay grant can set `payloadProfile: "strict"` to parse and forward canonical JSON while rejecting recognized provider-run tools, remote MCP, external URL inputs, provider file/container references, prior conversation state, and OpenAI background work; it sends OpenAI requests with `store: false`. Optional `allowedModels` exact-matches the requested model, `maxRequests` caps admitted requests for that verified session, and `maxInputBytes` lowers the existing 32 MiB request-body ceiling. `maxOutputTokens` caps each generation request using [Anthropic's `max_tokens`](https://platform.claude.com/docs/en/api/messages/create) or [OpenAI's `max_output_tokens`](https://developers.openai.com/api/reference/resources/responses/methods/create). When the client omits the output limit, the relay inserts the grant limit; a larger or invalid client limit is rejected before upstream. Anthropic token-counting requests do not generate output. Grants without these options keep their existing behavior and body bytes. The byte and output-token limits do not bound actual input tokens or guarantee a dollar cost ceiling, which also depends on the provider and model. They do not inspect prompt text, guarantee provider retention, or cover future provider fields. Native clients using provider-hosted files or conversation state need a broker-scoped design and compatibility tests before using it.

Destination-name denials alone are insufficient if an allowed host or local service can proxy to a protected endpoint. A strong confined profile needs default-deny external and host-loopback egress, with only narrow broker IPC and tested local services exposed. Probe each allowed service for arbitrary URL fetches, `CONNECT`, and other forwarding paths before treating the denial as effective.

The separate model relay streams synthetic native Claude Code and Codex turns through their custom gateway settings. The existing owned HTTPS action still buffers its response. The tests use a local bridge under the broker's UID, synthetic credentials, and fake TLS upstream; they do not prove installed agent identity, real provider/account behavior, or direct-egress denial. Claude Code sends a version-specific beta header that must be approved exactly. Stock Codex offers `web_search` and `namespace` provider tools, so the strict relay rejects it until that test client disables web search and multi-agent tool declarations. The clients' existing subscription sign-ins must not be treated as broker-owned credentials: the documented gateway paths can still send a client-held login token. An API-key or separately authorized OAuth relay may change billing, model availability, or client features and requires native acceptance before it can replace any existing sign-in workflow.

## macOS

The macOS native-surfaces CI job and the TypeScript/test/package job passed on commit `9a93801`. Those source and fixture results do not establish an installed signed Network Extension, a working privileged manager, or end-to-end isolation with two real macOS agent UIDs. The managed launch preflight below remains unsatisfied.

For a host-native agent on macOS 13 or later, install a signed, narrow LaunchDaemon/helper through ServiceManagement with the required administrator approval. Provision a pool of dedicated unprivileged local accounts during installation, then assign one account to each concurrent session; recycling an account requires closing its old sockets, revoking its grants, and proving that no process still holds its UID. The helper only accepts a vetted launch plan from the operator's s-gw process, prepares a session workspace, drops supplementary groups and UID/GID, and starts the agent. It must not become a general command runner. It closes inherited network and broker descriptors and creates no Internet socket before dropping UID. The s-gw broker can remain a LaunchAgent in the operator's login session so it can use the operator's authorized Keychain context. Its store stays readable only by that account.

**Managed launch preflight contract (not implemented).** An opt-in root manager must make the release decision inside its privileged launch path; a source-checkout script, a caller-supplied JSON assertion, and the acceptance fixture's `--check` result cannot authorize launch. Before releasing either of two agents, the manager must obtain these independent inputs and reject an absent, stale, or ambiguous result:

- Verify its own installed code requirement and the broker control peer's kernel identity and pinned code requirement. Check root ownership, canonical parent paths, modes, and extended ACLs for the manager, control and policy sockets, UID tombstones, and staged executable. The broker separately verifies that its store, recovery data, UI assets, and socket directory are outside both agent-readable or agent-writable trees.
- Resolve two preprovisioned `_sgwagent_` accounts from the OS, with distinct UIDs and GIDs, no existing process or live lease under either UID, private workspaces, and separate broker IPC paths. The root tombstone and broker lease must refer to the same launch before the UID is used. A stale account or uncertain process scan blocks launch.
- Verify a pinned code requirement for the installed Network Extension, its enabled socket-filter configuration, and a live provider attestation for the exact UIDs and sessions through the root-owned policy service. A service heartbeat or enabled configuration alone is insufficient: current-boot probes under each dropped UID must show direct IPv4, IPv6, DNS, UDP, host loopback, and operator-console denial while broker IPC and broker-owned egress work. Missing source audit tokens, provider crashes, policy changes, or a failed probe block or terminate the session. The provider and manager must prove denial remains effective between heartbeat checks.
- Read native acceptance evidence produced by the trusted root manager on this host, bound to the OS build, signed component identities, policy version, two real UIDs, and the tested native client. It must cover cross-agent IPC and descriptor transfer, UID-wide teardown, provider failure and recovery, and owned HTTPS/SSH actions. A copied fixture log or a test on another host is not launch evidence.

Only the trusted manager may turn all passing inputs into a release decision, immediately before execution, while retaining the ability to revoke and sweep both UIDs if a live gate fails. No manager, signed filter attestor, or such acceptance evidence ships here, so the present macOS source has no managed launch path that can satisfy this contract.

An additive runner scaffold is in `native/macos-agent-launcher/uid-runner.c`. It is not installed, wired to the CLI, or usable from an ordinary process. It requires real and effective root, an accepted Unix control socket on fd 3 whose peer is the broker account, and a separate root-owned network-policy service socket on fd 4. That service must keep the socket open and answer repeated `CHECK-V1 UID SESSION` frames with `READY-V1 UID SESSION` only while the effective filter is active. The runner schedules another check one second after each successful reply, bounds a reply to 1.5 seconds, and kills and sweeps the agent UID if the service disconnects, denies, or fails to answer. Neither socket service exists in the current product. A heartbeat alone cannot prove that the filter stays effective between checks or after provider failure; installed native acceptance must test those gaps. The fixed control, policy, and UID-tombstone paths now live under `/private/var/db/s-gw`, whose root-owned parent chain can satisfy the runner's no-write checks; `/private/var/run` is group-writable on the tested Mac and fails those checks. The runner checks socket ownership, mode, canonical path, parent chain, and extended ACL allow entries before trusting these paths. It requires a dedicated `_sgwagent_` account, a private root-owned UID lease directory, a staged root-parented workspace, and a broker-owned Unix socket. It records a nonreusable UID tombstone before fork, drops supplementary groups and UID/GID, changes to the agent workspace, closes every inherited descriptor above standard I/O, and requires the broker to acknowledge the UID/session after the agent identity connects. The future broker must actually verify that peer before acknowledging. It redirects standard streams to `/dev/null`; a trusted PTY bridge is needed for interactive agents. The network-policy service must attest to a supported, effective egress boundary before answering and keep that denial effective throughout the session; no such service or attestation exists. On exit, the runner scans all PIDs and sweeps processes holding the leased effective, real, or saved UID, including descendants that escaped its process group with `setsid`. A root-only `--teardown UID SESSION` path permits the trusted manager to repeat that sweep after a runner crash, but only for a dedicated account with a matching root-owned tombstone and broker control peer. Scan truncation, inspection errors, or surviving processes fail closed; neither path clears the tombstone or enables UID reuse. The PID/start-time check before each signal narrows the PID-reuse race but is not an atomic signal-to-process guarantee. The installer must independently prove no process remains before ever retiring that account.

`src/macos-agent-session.ts` provides a broker-owned, exclusive on-disk UID lease before registration with the verified Unix peer server. The UID tombstone remains even if registration fails or the broker restarts, so an old account is not silently reassigned. The lease directory must be created outside every agent-visible tree with broker-only access. A fresh account is required for another session unless a separate privileged teardown and recovery workflow is built and reviewed. Current unit tests use the broker account and synthetic UIDs; they verify lease persistence and fail-closed validation, not isolation between two real macOS accounts.

The optional `acknowledgeMacAgentLaunch` handler in `src/macos-agent-probe.ts` can be used as the `onConnection` callback of the verified Unix peer server for the runner's one-shot launch probe. The runner half-closes its write side after `HELLO-V1 <kernel UID> <registered session ID>\n`. The handler requires that exact frame followed by EOF within 1.5 seconds, sends the matching `READY-V1` only after the native `getpeereid` adapter has registered that peer, and closes the probe connection. Delayed extra bytes and a complete frame without EOF are denied. The claimed UID and session text never create or change a principal. This handler is not connected to the CLI or a working agent request protocol. Its real-socket tests use the current user as a synthetic agent identity; two provisioned UIDs and an installed root runner are still needed to prove the boundary.

`scripts/test-macos-two-uid-acceptance.mjs` is an opt-in, source-checkout-only broker-side native acceptance fixture; it is not included in the npm package. It requires an explicit JSON plan with `purpose: "s-gw-macos-two-uid-acceptance"`, `dedicatedTestHost: true`, `leaseDir`, `stagedAgentScript`, `brokerCanary`, `nodeExecutable`, and exactly two `agents`. Each agent entry supplies a preprovisioned `_sgwagent_` account, its numeric `uid` and `gid`, a unique `sessionId`, a `0700` workspace with a `0700` `tmp` child, and separate `socketPath` and `reportSocketPath`. The lease, staged script, canary, workspace, and broker socket paths must be under `/private/var/db/s-gw-acceptance/`. The staged script is a root-owned, agent-readable copy of the fixture with the same SHA-256 digest; broker socket parents are broker-owned and agent-traversable. The broker account must be a trusted supplementary member of both distinct agent socket groups so its unprivileged `chown` can assign each new socket to the intended group; the agents retain only their own primary group after launch. A privileged prebind design would be needed if that broker group membership is not acceptable. From a built checkout with `dist` and the native peer helper present, run `node scripts/test-macos-two-uid-acceptance.mjs --check /absolute/plan.json` as the non-root broker account for read-only owner, mode, canonical-path, account, group-membership, and extended-ACL checks. The check fails if the fixed broker-owned control socket, root-owned policy socket, or root UID-tombstone directory is absent or unsafe. It does not prove those services' behavior.

On a dedicated host with independently provisioned root manager and effective network-policy service, `--run` creates only the acceptance broker sockets and persistent broker-owned UID leases. It emits exact `runnerArgv` arrays for the trusted root manager; it never creates accounts, installs services, invokes `sudo`, or starts the root runner itself. Launch both plans through that manager while the fixture waits. The runner first sends its own launch probe, then the staged fixture process checks its real/effective UID and GID and rejects unexpected supplementary groups. The fixture verifies native `getpeereid` admission, wrong UID and session rejection, cross-agent socket denial, access denial for a broker-only canary and the other workspace, and denial of IPv4/IPv6 host-loopback TCP and UDP that the broker can reach. It also creates a world-accessible Unix socket in a broker-owned, agent-traversable directory. The broker must connect to that socket, while both agents must be denied; the fixture rejects extended ACLs on the socket and its parents so an ACL cannot make that probe pass without an effective local IPC boundary. This catches a reachable local service that could forward agent traffic outside s-gw. Set optional `hostIpv4Probe` to an active, non-loopback IPv4 address on the test Mac to also require TCP and UDP denial to a broker-reachable listener on that interface; this detects a policy that blocks only loopback. Each agent then holds a separately authenticated probe connection open. The broker revokes its probe registration while the agent is alive; both sides must observe that connection closing, and a new connection must receive no acceptance frame. A separate result socket stays registered for the final report. The fixture keeps broker UID tombstones after stopping both peer registrations and rejects reuse. An optional `fdTransferProbe` adds a root-owned native helper and a root-owned sticky shared rendezvous directory. It attempts to pass a live broker-authenticated Unix descriptor from one agent UID to the other via `SCM_RIGHTS`; use by the other UID fails acceptance, while a timeout without an explicit OS denial is inconclusive. Compile and stage `scripts/macos-agent-fd-transfer-probe.c` at the plan's `helperExecutable` and supply a nonexistent `rendezvousPath` inside a root-owned `01777` shared directory under the acceptance root. The local helper roundtrip tests the transfer mechanism, not the two-UID boundary. A passing fixture is only one acceptance component: the root manager must independently attest runner provenance, root UID tombstones, effective network-policy enforcement beyond loopback, UID-wide teardown and PID reuse, plus native client and owned HTTPS/SSH behavior. No such root manager or policy service is installed by this repository, and this fixture has not run with two real UIDs.

Before installed use, the root and broker lease records must be coordinated with an atomic launch record. The root runner rejects extended ACL allow entries on its checked paths. The source-only TypeScript broker rejects extended ACL allow entries on its lease, socket-directory, peer-helper, and parent paths using macOS `ls -e`; it checks the peer helper ACL at listener startup rather than on each connection. The broker still accepts root-owned sticky parents such as `/private/tmp`; the runner refuses those paths, so a shared installed path needs a non-sticky parent. These path checks are not atomic with later use. Inspect effective macOS ACLs as the provisioned agent UID across both sides and reject any broker path the agent can alter. Test UID-wide teardown, retained network denial, and the broker handshake with two real accounts; the present tests use synthetic process listings and do not cover these boundaries. Verify on each supported macOS version that `PROC_ALL_PIDS` and `proc_pidinfo` cover processes retaining only the agent's saved UID, that the fixed scan cap and inspection failures stop launch and teardown safely, and that no reachable privileged executable lets the agent shed all three UIDs. Keep the tombstone and deny account reuse if any check is inconclusive. `getpeereid` identifies the process that connected; a connected descriptor passed to another agent can retain that identity. A host-native deployment must prevent cross-agent descriptor transfer through reachable IPC, or use separate VMs and host-owned per-session transport to make that boundary enforceable.

For each concurrent session, use a distinct agent UID. Grant that UID access only to the selected workspace and its broker Unix socket; deny the operator home, Keychain, other session directories, and direct network egress. A repository inside a `0700` operator home cannot simply be opened by another UID. Stage a scoped checkout outside that home under a launcher-controlled directory, or use an audited access mechanism that exposes only that checkout; changing the home directory to world-traversable would expose other known paths. Put the socket under a broker-controlled directory that the agent can traverse but cannot replace. On the accepted socket the broker calls `getpeereid`, maps the returned effective UID to its live launcher record, and rejects anything else. XPC audit tokens and code-signing requirements can add checks for the packaged helper, but signing identifies an executable, not arbitrary agent code running inside it. A plain Seatbelt sandbox under the operator's UID is not a distinct principal.

The accepted socket keeps the identity of its original connector. If an agent can pass that file descriptor through a shared Unix socket to another UID, the receiver can use the first agent's grant. Keep each agent's IPC endpoints and writable socket paths separate, block cross-agent descriptor passing, and include a deliberate `SCM_RIGHTS` transfer attempt in native acceptance.

For host-native CLI agents, Apple's supported path for a product that blocks socket flows is a Network Extension content-filter system extension. A `NEFilterDataProvider` can decide whether to allow or drop new flows; `filterSockets` must be enabled, and source process/app audit tokens can help classify the agent. `sourceProcessAuditToken` is nullable and available on macOS 13 or later; a system process may connect on an app's behalf, so source process and source app can differ. Treat an absent or ambiguous token as unclassified, never as permission. The extension must use the appropriate Developer ID entitlement and be installed and enabled before the launcher releases an agent. Do not treat a binary signing identifier or a claimed PID as the agent principal. Only a flow actually delivered to and dropped by the effective provider is denied; the broker's `getpeereid` check separately supplies IPC identity. Apple's deployment technote lists macOS content-filter system extensions from macOS 10.15 and supports Developer ID distribution. Entitlement, provisioning, notarization, extension activation, and filter configuration still need to be verified for the shipped build. Provider behavior after a crash, removal, sleep/wake, and system update, and its coverage of loopback and non-socket traffic, remain native acceptance gates. The product must not launch a confined agent if any required denial cannot be proved active.

Apple explicitly says Packet Filter is not an API for a widely distributed product and directs socket blockers to Network Extension. PF anchors and deprecated `sandbox-exec` profiles are unsuitable as s-gw's shipped enforcement guarantee. Apple also says its new URL filter does not automatically cover applications outside WebKit and URLSession, so it cannot enforce this boundary for arbitrary native agents. A signed App Sandbox without the `com.apple.security.network.client` entitlement is another host-native candidate. One disposable probe on macOS 27.0.1 denied IPv4 and IPv6 loopback TCP for the sandboxed executable and an unsigned child, while an entitled control connected; a temporary Unix socket was also denied. This does not establish native agent compatibility or a usable broker IPC route. A sandbox-compatible IPC path, child behavior, and effective isolation with the actual packaged agent need acceptance before relying on it.

For the stronger macOS option, run each untrusted agent in its own Linux VM using Apple's Virtualization framework. Set `networkDevices = []`, verify the live VM exposes no network device, and expose only a dedicated virtio socket endpoint to a host broker bridge; give the guest a scoped workspace and no host credential or broker-store mount. The host launcher assigns the VM/session identity from its own live VM object, not a field supplied by the guest. The bridge forwards a restricted request protocol to s-gw, which still decides approvals and owns TLS/SSH execution. Host-side broker and operator UI paths remain outside the VM. This changes native macOS agent behavior and file access, so it is an opt-in design until compatibility and user approval support a migration. A VM without a network device still needs acceptance tests for every other host channel: shared directories, clipboard, serial/virtio devices, host services exposed by the bridge, and cross-VM forwarding.

For either host-native or VM mode, the launcher must fail closed if it cannot verify the isolation plan. Probe direct IPv4, IPv6, DNS, UDP, host loopback, and access to the operator console and other agents' IPC paths; guest-local loopback may remain available for agent tools. Verify that broker IPC still works and no connected network descriptor was inherited. Treat that adapter's cgroup lookup as a guard on top of the unique UID and trusted launcher, not as independent proof of the current socket holder. The opt-in model relay requires the Linux verifier in `src/linux-peer-identity.ts` and `native/linux-peer-identity/verify.c`. It uses `SO_PEERPIDFD`, checks the stable peer process is live before and after reading its cgroup, and fails closed if the kernel lacks that socket option. Build it with `npm run build:linux-peer-identity`. The verifier still identifies the process that connected, not a later holder of a passed socket. The launcher must prevent cross-boundary descriptor passing and cgroup migration before cgroup membership becomes an authorization boundary.

For a native model client that only speaks HTTP, `src/agent-local-model-forwarder.ts` now has an opt-in Linux source path. The gated manager writes a root-owned attestation after inspecting the live unit and before releasing it. The forwarder checks its UID, cgroup, private network namespace, read-only proof mount, and mounted broker-socket inode before binding `127.0.0.1`, then rechecks for each accepted connection. It copies bytes to the fixed Unix listener, which authorizes the forwarder's kernel peer identity instead of an HTTP header. The forwarder accepts at most eight live TCP connections. It requires the root-owned socket handoff so the socket parent inside the agent root is not agent-writable. No service installs or starts this forwarder yet, and a same-UID or host-loopback test does not prove isolation. Native two-UID Linux and model-client acceptance remain required.

## Windows

Prefer a distinct AppContainer SID for each concurrent agent session. Create a session profile with `CreateAppContainerProfile` and launch the agent using `PROC_THREAD_ATTRIBUTE_SECURITY_CAPABILITIES`; a less-privileged AppContainer additionally needs `PROC_THREAD_ATTRIBUTE_ALL_APPLICATION_PACKAGES_POLICY` with `PROCESS_CREATION_ALL_APPLICATION_PACKAGES_OPT_OUT`, if the CLI supports that environment. Ordinary AppContainers may retain access through `ALL APPLICATION PACKAGES` ACL entries; test effective access to the store, helper and its parent directories, console assets, and IPC objects under the actual package token. Create the process suspended, place it in a Job Object with kill-on-close and no breakaway, install and verify IPv4/IPv6 Windows Filtering Platform rules tied to `FWPM_CONDITION_ALE_PACKAGE_ID`, then resume it. The launcher must terminate or hold the agent if the Base Filtering Engine stops or a required rule disappears. The Job Object controls lifetime but is not the authorization identity. The broker runs at normal full trust outside the AppContainer and keeps its store and credential access under the operator account. If a CLI cannot run correctly in AppContainer, use a dedicated local account for the session with equivalent ACL and network restrictions using `FWPM_CONDITION_ALE_USER_ID`; this requires a privileged setup path.

Expose a local named pipe with an explicit security descriptor granting only the intended agent SID and broker identity; use `PIPE_REJECT_REMOTE_CLIENTS`, `FILE_FLAG_FIRST_PIPE_INSTANCE`, and the `\\.\pipe\LOCAL\<name>` namespace where required. Do not grant the client pipe-instance creation rights. After reading a request, the server calls `ImpersonateNamedPipeClient`, opens the client token, inspects its account or AppContainer SID and logon session, and matches it to an active launcher record. It checks impersonation success and level before processing and always calls `RevertToSelf`. Pin the process returned by `GetNamedPipeClientProcessId` and verify membership in the registered Job; the PID or Job name alone is not an authorization identity. Do not use the default named-pipe ACL, which grants broader read access.

An opt-in, one-request pipe foundation is in `src/windows-agent-pipe.ts` and `native/windows-peer-identity/one-shot.c`. The broker registers a launcher-attested user SID, optional AppContainer package SID, logon LUID, Windows session number, fresh `Local\s-gw-agent-<32 lowercase hex>` Job name, and nonsecret session ID. It burns each SID, Job name, and session ID for that broker process, limits the session to eight pending exchanges, and requests helper termination on revocation. Each helper creates an unpredictable `\\.\pipe\LOCAL\s-gw-...` name with `FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS`, one message-mode instance, an explicit protected DACL, and a low-integrity label. Client ACEs grant data read/write and no `FILE_CREATE_PIPE_INSTANCE` bit. For AppContainer clients, both the user and package SID have those data rights. A client must request those specific rights; a generic-write open requests instance-creation rights and should fail. The helper opens the launcher-registered named Job with `JOB_OBJECT_QUERY` and rejects missing Jobs, Jobs without kill-on-close, or Jobs that permit breakaway. It closes that query handle before waiting for a pipe client, so it does not keep the Job alive if the launcher exits. It reads one bounded message (32 KiB), impersonates its sender, checks the impersonation level, token user SID, AppContainer SID and status, logon LUID, and Windows session number. It reopens and rechecks the Job, then pins the original connecting process by kernel-reported PID and requires that live process to belong to the Job before passing request bytes to the broker. It closes its query-only Job handle after admission so the launcher's retained handle still controls kill-on-close. The broker callback receives a principal derived from the registered SID, never a client-provided name. A response is returned over the same pipe. Build the helper on a Windows MSVC host with `node scripts/build-windows-peer-identity.mjs`.

This code is not installed or connected to the ordinary MCP server, model relay, console, or a Windows agent launcher. The TypeScript wrapper requires an installer-pinned helper hash and invokes the read-only ACL and hash check in `src/windows-peer-helper-acl.ts` on every attempted native opening. It still refuses native launch until the agent launcher and network boundary are verified on Windows. A production launcher must generate the Job name, create the Job before broker registration with a restrictive security descriptor, reject `ERROR_ALREADY_EXISTS`, retain its owner handle, assign the suspended agent before resuming it, and register the name through a control path that an agent cannot call. The name must never come from a pipe client or agent request. The inspector checks each existing path component and its raw ACEs, but it is not an `AccessCheck` against the actual agent token and has not run on Windows. Path spelling alone cannot prove the ACL property. Shared-host Windows CI compiles the helper and fixtures, runs fail-closed pipe cases and the WFP revocation self-test with two temporary AppContainer profiles, and compares read-only system-root ACL snapshots. It does not launch an agent. The full two-agent exchange now requires a separate fixed NTFS/ReFS test volume and a prepared isolated Windows runner. Its read-only preflight checks exact metadata ACEs on both roots and compares their ACL snapshots after the run; no test code writes the system-drive root. The earlier disposable DACL preflight failure (control flags `0x0404` to `0x0004`) remains evidence that the shared runner cannot safely be prepared in place. The helper uses blocking I/O inside a disposable child process; the broker wrapper applies a deadline and terminates that child, rather than relying on `CancelIoEx` to free an in-use buffer. Revocation also aborts the broker callback's signal, but the eventual handler must honor that signal and recheck policy immediately before any credential-backed execution. Native Windows acceptance must prove the child actually exits on deadline and revocation, the AppContainer dual-principal and low-integrity checks behave as expected, the pipe rejects remote clients and instance creation, and two distinct agents cannot impersonate one another. The new Job check is source groundwork. If the launcher closes its last Job handle during the brief membership check, the helper's query handle may delay termination until it closes; a production control channel must revoke the broker session at launcher death before any pending action executes. The native CI fixture creates a Job under the broker test account; it does not prove production Job ACLs or launcher control-channel provenance. `GetNamedPipeClientProcessId` identifies the process that opened the pipe, not necessarily a later process holding a duplicated connected handle. The connected-handle gate has a real in-Job AppContainer open the broker pipe, then attempt to copy that handle into a same-profile target suspended in a different Job and into the ordinary full-trust test host outside the registered Job; successful duplication fails CI. Passing these gates would cover those transfer paths only. It cannot prove that a handle transferred by inheritance, a privileged intermediary, or some other route will be rejected by the pipe helper. A production launcher must prevent out-of-Job same-profile processes and audit handle inheritance and sharing. The launcher still needs AppContainer or dedicated-account creation, a retained kill-on-close Job, WFP rules, persistent SID reuse prevention across broker restarts, and a client that opens the pipe with the exact rights above. Until those pieces and native tests exist, this foundation does not establish Windows confinement or close a bypass in the default product.

The Windows native CI fixture creates two temporary AppContainer profiles with distinct package SIDs. It stages each child executable and a readable file control in a disposable directory inside that AppContainer's own profile folder, without changing ACLs on the host user's Temp ancestors. It places each broker-only canary under the host-owned temporary fixture root, outside the writable AppContainer profiles. Each child probes denial of read, write, delete, ACL-change, and sibling creation rights while the host reads its canary before and after the run. The fixture checks each child token against its assigned package SID, requires a named-pipe ACL denial in both cross-agent directions, rejects a same-profile process outside the registered Job, launches a child suspended into a kill-on-close Job Object, and checks that it cannot reach IPv4 and IPv6 host-loopback TCP listeners that the host can reach. The fixture Job has a protected broker-only DACL, and each AppContainer must receive `ERROR_ACCESS_DENIED` when opening it for query, assignment, limit changes, termination, or DACL/owner changes. While one agent holds its verified broker pipe open, the other must be denied `PROCESS_DUP_HANDLE` on that agent's process and on the pipe-owning broker, in both directions. Another connected client attempts `DuplicateHandle` into a same-profile process in a distinct Job and into the ordinary full-trust test host outside the registered Job; either `OpenProcess` or the duplication itself must return `ERROR_ACCESS_DENIED` for both targets while the normal request/reply still succeeds. A separate same-profile process in another Job must also be denied `PROCESS_DUP_HANDLE` on that connected client, blocking the direct pull path. The prepared-host workflow has not yet produced a native Windows result. The fixture launches each child with a fresh allowlisted environment containing only trusted Windows system paths and a profile-local working directory; a synthetic parent environment canary must be absent in the child. The full prepared-host mode captures unique DNS names from both Windows lookup APIs with a host-positive resolver control; shared-host CI does not run this probe. They test the fixture's canary boundary and absent network capability, not the installed store ACL, a production launcher, external egress, or a complete WFP policy.

`native/windows-peer-identity/wfp-boundary.c` now supplies a package-SID WFP deny for IPv4/IPv6 outbound connect, listen, and receive/accept layers. The fixture installs all six hard-block filters transactionally before it resumes an AppContainer child, reads them back, and checks them during its normal process wait. It closes the dynamic WFP session during cleanup. A native self-test deletes one agent's filter, requires that agent's health check to fail while the other agent stays healthy, and checks that closing the second session removes its filter. This needs WFP policy rights on the Windows test host. The previous shared runner passed this self-test before reaching the ACL gate; the revised shared-host path retains it, while full AppContainer launch remains unproved. Its existing loopback test still cannot attribute denial to WFP because the fixture grants no network capability. A production supervisor must hold the Job and WFP session together, terminate the Job if BFE or a rule fails, and prove that no network-capable process can run during a WFP restart or supervisor crash. The module is not yet wired into an installed launcher or broker registration path.

The WFP package filters also do not prove that DNS names cannot leak. Windows normally passes name lookups to the DNS Client service, which can query a configured resolver on behalf of an application. If that service sends an agent-chosen name under its own identity, a package-SID socket rule might not match the outbound DNS flow. This is a plausible bypass, not a reproduced result. The prepared-host fixture now binds synthetic UDP resolvers on `127.0.0.1` and `::1`, requires every active adapter to use only those addresses for DNS, proves a fresh host `GetAddrInfoW` query reaches the resolver, then rejects any captured name from either agent's fresh `GetAddrInfoW` or `DnsQueryEx` calls. It does not alter the host DNS configuration. This configured-resolver path has not run on a prepared host, and the intended DNS-over-HTTPS policy and other network paths still need separate capture. Windows DNS egress remains unproved until those tests pass. [Microsoft DNS Client lookup flow](https://learn.microsoft.com/en-us/windows-server/networking/dns/queries-lookups)

An agent-local HTTP forwarder may be needed for stock model clients; it must use the named pipe for broker requests. AppContainer loopback is normally blocked. If native client compatibility requires a loopback exemption, pair it with a WFP rule that allows only that session's relay address and port; a broad exemption would expose other host-local listeners. Windows named-pipe/AppContainer support and CLI compatibility need native Windows acceptance testing.

## Acceptance and rollout

Use synthetic credentials and two concurrent agents with different OS identities. Prove that each can request its own approved action, cannot claim the other's principal by changing MCP names/environment/request fields, cannot connect as the other identity, cannot read the broker store or the other's private files, and cannot reach protected services directly. Kill a session during a reusable action and prove revocation. Test real native model sessions and owned HTTPS/SSH under the same profile on macOS, Linux, and Windows before enabling it by default.

For host-native macOS, first install the two root-owned socket services and an effective, supported network-denial provider, then run the native runner with two provisioned `_sgwagent_` accounts. Verify that `getpeereid` reports each separate UID, not just a synthetic UID registered by the broker's own account. Deny direct connections from each account across IPv4, IPv6, loopback, and UDP, including after the provider is disabled or crashes; a failure to prove denial blocks launch. Kill the runner and a descendant that has called `setsid`, and verify that the broker rejects its old UID after restart and the installer refuses account reuse while any process remains. For VM mode, verify that the guest has no network interface and cannot reach the host except through its own restricted virtio socket; an agent inside one VM must not borrow another VM's session. Test the future PTY bridge and native client startup separately; the current runner deliberately has no interactive stdio.

Add an explicit malicious-peer test: Agent A attempts to read Agent B's launch manifest, borrow its IPC handle, reach B's broker endpoint through every available proxy, and load the operator console on each local listener. The expected result is denial before a credential-backed request is created. Repeat with an ordinary local service intentionally allowed to A, so the test detects accidental loss of that existing access.

The ordinary MCP server and current same-user Anthropic launcher remain compatibility paths for request submission and one-time manual approval. Their claimed names cannot authorize unattended use. A partial peer-credential helper added to the current same-UID launcher would not establish managed-agent identity.
