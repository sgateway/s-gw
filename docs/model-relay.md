# Broker-owned model relay

## Status

The streaming transport in `src/model-relay-transport.ts` and Unix HTTP listener in `src/model-relay-server.ts` are opt-in broker APIs. The listener accepts connections only after the native peer helper verifies the Unix socket peer and the broker matches its UID to a registered live session. On Linux it additionally requires the pidfd-backed verifier and fails closed if its helper or the kernel socket option is unavailable. The trusted in-process caller registers one fixed provider and s-gw API-token handle per session for at most 30 minutes. An agent cannot register a session or choose a handle over HTTP. A source-only managed Linux service can now run this listener alongside verified MCP for one root-managed agent session; it has no installed production units or production native-client acceptance yet. The current same-UID Anthropic launcher cannot establish the distinct OS identity required to use this listener as a confinement boundary.

The ledger now has a first-class `model_relay` request. A trusted launcher can create it for a verified principal and session; it binds the exact handle, provider, route subset, account IDs, API version, allowed beta values, and lifetime. The operator console or CLI can approve it once. Timed, login-session, and always-allow choices are rejected for this action, and ordinary command execution cannot claim it. Scoped deny and ask policies can name `model_relay`; explicit allow policies are rejected, and preexisting broad allow policies do not autoapprove relay requests. `StoreBackedModelRelayApprovals` claims a request before listener registration and rechecks the persisted request and handle policy for each broker operation. On session end it revokes in-memory authorization first, then writes the terminal ledger state. A failed write emits a nonsecret broker warning or calls the operator's error hook immediately. The adapter retains the end record for an idempotent retry on listener close, and close reports the original failure. If the broker exits before a retry succeeds, the request can remain `executing` until a later store mutation reaps it after the longer of its approved lifetime and the ten-minute stale-execution window. A claim must occur within five minutes of approval. A restarted broker has no active in-memory claim, so old executing requests fail closed. The listener also accepts a custom in-process verifier for tests and integrations; never wire a no-op verifier into an agent-reachable service.

The handle must be an `api-token`, allow `s-gw:model-relay`, and allow the exact `api.anthropic.com:443` or `api.openai.com:443` destination. The listener rechecks approval, store policy, session lifetime, and handle existence during streaming. Registration remains a trusted control-plane API outside the agent boundary. The opt-in Linux managed service attaches the durable approval to its root-attested launch gate. Synthetic native Claude Code and Codex turns pass through disposable test relays, but no installed native agent client has been qualified with it.

The relay has fixed upstreams: `api.anthropic.com` for Anthropic Messages and `api.openai.com` for OpenAI Responses. It never accepts an upstream URL from an agent, does not implement `CONNECT`, and does not intercept TLS. It drops the client's `Authorization`, `x-api-key`, cookies, proxy authorization, and routing/account headers; the broker writes its own bearer credential. The broker fixes the Anthropic API version and may grant exact beta header values; other agent beta values fail closed. An operator-owned workspace, project, or organization ID may be supplied by the trusted caller. Each grant admits only its approved subset of the fixed provider routes.

Allowed requests are `POST /v1/messages` (including Claude Code's `?beta=true`), `POST /v1/messages/count_tokens`, `GET /v1/models` (optional model discovery), and `POST /v1/responses`. Redirects, compressed responses, unsupported methods and queries, untrusted TLS, and private DNS results fail closed. Responses stream with backpressure and bounded memory. The transport rechecks authorization during the stream and withholds exact echoes of the broker credential, including split-chunk, upper- and lowercase percent-encoded, JSON-escaped, base64, and unpadded base64url forms. Arbitrary transformations of the credential or echoes of a different secret remain outside this transport's guarantee.

Each request body may be up to 32 MiB. A trusted grant can set `maxInputBytes` to a smaller per-request byte limit and `maxOutputTokens` to a per-generation limit. The relay inserts the output limit when it is omitted and rejects a larger or invalid value before contacting the provider. Anthropic `max_tokens: 0` remains valid for cache warming; OpenAI's minimum is 16. Anthropic token-counting requests have no generation limit. Grants without these options keep their existing request bytes. The limits do not cap input tokens or guarantee a cost ceiling.

Across active uploads, the transport retains at most 64 MiB of request chunks; the verified listener also limits each session to 32 MiB of those buffers. It returns 503 when either budget is full and releases a reservation after the upstream write finishes or the request ends. Concatenation and TLS writes can briefly use more memory, so this is a request-buffer budget rather than a process-memory ceiling. The Unix listener supplies separate connection and stream limits.

The Unix listener allows four active requests per session by default, configurable from one to eight by the trusted caller, and at most 32 active requests across sessions. Broker approvals and store operations have deadlines and a separate limit of 32 unresolved operations. A timed-out operation keeps its slot until its underlying work settles, so a hung callback can exhaust that budget and fail closed. The peer adapter limits each session to eight sockets and 32 pending verifications. HTTP headers have a 10-second deadline, request bodies a 20-second idle deadline and a 60-second total deadline, and each socket accepts one request. Stopping or expiring a session closes its sockets and active streams. The listener is not exposed on TCP.

`src/agent-local-model-forwarder.ts` is an opt-in Linux source foundation for a client that needs an HTTP base URL. It copies TCP bytes from `127.0.0.1` inside one agent network namespace to the root-attested broker Unix socket; it does not parse authorization headers or select a session from HTTP input. The combined managed service mounts its model socket at `/run/s-gw/model.sock`, supplies that nonsecret path in `SGW_MODEL_RELAY_SOCKET`, and records the same socket in the launch-gate attestation. MCP-only plans retain their prior socket path, but old root-provisioned plan records need reprovisioning with the MCP socket unit file and its root-control lifetime binding before this broker accepts them. Startup requires a root-owned read-only launch-gate attestation issued after the systemd manager checks the live UID, cgroup, private network namespace, and socket. It checks those facts again before accepting each connection. It refuses same-UID, host-network, writable proof, altered socket, and unsupported-platform starts. The root-owned socket handoff is required for a socket whose parent is root-controlled. There is no installed forwarder process, native model-client routing, or real two-UID acceptance yet. The synthetic byte-bridge tests use a same-UID TCP server only inside the test harness; they do not establish a confinement boundary.

## Root-managed Linux combined service

The optional `linux-managed-mcp` configuration adds `plan.modelRelaySocket` at `/run/s-gw/agents/<session>/model.sock` and `relay: { grant, requestId? }`. The plan must use the existing full launch-gated, systemd-supervised profile with a root-attested `identityGeneration`. The grant must include `payloadProfile: "strict"`, a finite `ttlMs`, a model provider, and an s-gw API-token handle. It contains no bearer value. The root-owned plan record additionally names `s-gw-managed-model-<session>.socket` in `modelRelaySocketUnitFile`. The MCP-only configuration fields remain valid. A root-provisioned plan record created before the MCP socket lifetime check must be regenerated with `mcpSocketUnitFile`, and its socket unit must use `BindsTo=` plus `After=` on root control. This source-only profile has no installed production provisioner; an old record fails closed until the root owner reprovisions it.

Provision the request before starting the agent. A root operator can run `node <root-owned-runtime>/control/linux-agent-control.js --prepare <session-id>` while the root control service is running and the broker and agent units are stopped. Root control verifies the registered plan, exact broker unit and config, and both socket units. It stops both sockets before starting the pinned broker unit, so no agent connection can newly queue during the trusted transaction. The broker must have no inherited listener FDs and must consume the short-lived root authorization for the exact config bytes before creating a request for `linux:managed:<identityGeneration>` and the exact session. The command returns the durable request ID after the broker exits cleanly. A repeated command returns that same pending or approved ID only if the principal, name and grant still match; the agent never starts during preparation. The operator reviews the handle, provider, route and strict grant, and approves the ID with `s-gw approve <request-id> --mode per-transaction` or the operator console. Root then seals the ID into the root-owned broker config and starts both socket units. Start the same broker service within five minutes of approval. It must inherit exactly two named listener FDs, start MCP and relay with Linux per-message gates, launch and attest the agent under the gate, claim the approved relay grant, register both listeners for that one session, recheck both socket bindings, and only then release the gate. A mismatch or failure keeps the agent from executing and revokes or fails the claimed request. On session stop or root-control loss it revokes both endpoints and ends the relay ledger record.

An activated combined broker now refuses a relay config without a sealed request ID, whether the MCP socket or model socket starts it. It checks this before opening the store or creating a request. The no-descriptor preparation entry still requires a matching short-lived authorization from the root-only `--prepare` command for the exact registered config; starting the broker service directly without that authorization fails. Existing unsealed combined configurations must use the root preparation, approval, config-sealing, and socket-start sequence above. Queued clients cannot create approval requests. To restore the former socket-triggered preparation workflow, stop both socket units and the broker, take paired store snapshots, and revert the entrypoint's activated-socket rejection and mandatory root authorization in a compatible build. That rollback restores agent-triggered request creation and the queued-client restart risk. Barry approved this change for the source-only Linux managed relay; ordinary MCP and non-managed model paths are unchanged.

Both `.socket` units target `s-gw-managed-mcp-<session>.service` and bind to `s-gw-agent-control.service`. They are stopped during trusted preparation and active for approved runtime launch. The MCP unit uses `ListenStream=/run/s-gw/agents/<session>/broker.sock` and `FileDescriptorName=s-gw-agent-<session>`. The second unit is:

```ini
[Unit]
Description=s-gw managed model relay socket
BindsTo=s-gw-agent-control.service
After=s-gw-agent-control.service
[Socket]
ListenStream=/run/s-gw/agents/<session>/model.sock
SocketUser=root
SocketGroup=<dedicated-agent-group>
SocketMode=0660
DirectoryMode=0711
PassCredentials=yes
FileDescriptorName=s-gw-model-<session>
Accept=no
RemoveOnStop=no
Service=s-gw-managed-mcp-<session>.service
```

The broker checks the live second socket unit's root-owned file and service association, each activated FD's exact socket node and inode, and the systemd agent unit's read-only mounts for both paths. The message gates require `SO_PASSCRED` and `SO_PASSPIDFD` on both listeners. A copied request ID or agent-supplied HTTP header cannot register a grant. Source tests cover the configuration, FD manifest, unit properties, and cleanup. The opt-in native Linux CI fixture now attempts two-agent descriptor-transfer checks and broker-owned TLS streaming to a synthetic local provider. That lane has not run in this checkout; a real provider and native client still need acceptance before an installed confinement claim.

## Current verification

`npx vitest run tests/model-relay-server.test.ts tests/model-relay-transport.test.ts` uses a synthetic HTTPS provider behind a test-only transport seam. It proves incremental SSE delivery, exact upstream routing, client credential stripping, broker credential substitution, split credential redaction, optional Anthropic routes, OpenAI Responses routing, redirect refusal, authorization refusal, TLS trust failure, grant byte and output-token limits, and the concurrent request-buffer limit with a full 32 MiB request. The listener test exercises the native Unix peer helper, rejects an unregistered peer, ignores agent-supplied handle headers and queries, enforces the handle policy and approval callback, limits active requests, and closes an active stream on session stop. It also checks durable approval after a store reopen, rejection of forged principal objects and cross-session claims, refusal of reusable approval, route-subset enforcement, policy deny and handle deletion, and finite expiry. Its one test peer runs under the test account with only the registration guard mocked; this is not proof of distinct OS isolation or native-agent end-to-end behavior.

The opt-in `SGW_TEST_MANAGED_RELAY=1` native Linux CI lane uses a disposable loopback IP alias and a root-owned hosts file mounted into only the broker unit. The unit checks that its private hosts mapping is active before the broker starts. A local HTTPS server presents a certificate for `api.anthropic.com`; the broker still resolves that fixed hostname, checks the resulting address, and verifies TLS. Each managed agent must fail a direct connection to the synthetic provider IP, receive one SSE event before the fixture releases the second, receive a redacted split bearer echo, and hold another stream open until its broker or root control stops. The fixture checks upstream bearer substitution, rejected agent headers, request body, and stream cancellation. The ordinary MCP-only lane is unchanged. Passing this synthetic lane will not prove real provider behavior or a native Claude Code or Codex turn.

`tests/native-claude-model-relay.test.ts` runs only with `SGW_TEST_NATIVE_CLAUDE=1`; `tests/native-codex-model-relay.test.ts` runs when the bundled macOS Codex CLI is present. Both isolate client state, deny nonlocal network access through macOS Sandbox, use a test-only same-UID TCP-to-Unix bridge, and serve synthetic SSE from fake TLS upstreams. They prove strict grant admission, native client parsing, and broker credential substitution for one text turn. Claude Code currently sends `HEAD /api/hello` before its approved Messages request; the unsupported HEAD gets a 404 without blocking the turn. The test preflights Claude's exact beta header before granting it. Codex needs web search and multi-agent tool declarations disabled for this strict turn, since its stock request advertises provider tool types outside the strict allowlist. These tests do not establish a real two-UID identity or installed network boundary, account and billing behavior, or full native tool/cancellation compatibility.
