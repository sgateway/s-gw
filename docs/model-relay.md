# Broker-owned model relay

## Status

The streaming transport in `src/model-relay-transport.ts` and Unix HTTP listener in `src/model-relay-server.ts` are opt-in broker APIs. The listener accepts connections only after the native peer helper verifies the Unix socket peer and the broker matches its UID to a registered live session. On Linux it additionally requires the pidfd-backed verifier and fails closed if its helper or the kernel socket option is unavailable. The trusted in-process caller registers one fixed provider and s-gw API-token handle per session for at most 30 minutes. It must provide a broker-side approval verifier; an agent cannot register a session or choose a handle over HTTP. There is no CLI flag, durable model-relay approval action, privileged launcher integration, or native-agent routing yet. The current same-UID Anthropic launcher cannot establish the distinct OS identity required to use this listener as a confinement boundary.

The listener checks the approval callback and store policy before resolving the handle inside the broker. The handle must be an `api-token`, allow `s-gw:model-relay`, and allow the exact `api.anthropic.com:443` or `api.openai.com:443` destination. It rechecks approval, store policy, session lifetime, and handle existence during streaming. Grant registration and the approval callback are trusted control-plane APIs; the present module does not persist approval or issue a grant from an operator UI. Do not wire a no-op approval callback into an agent-reachable service.

The relay has fixed upstreams: `api.anthropic.com` for Anthropic Messages and `api.openai.com` for OpenAI Responses. It never accepts an upstream URL from an agent, does not implement `CONNECT`, and does not intercept TLS. It drops the client's `Authorization`, `x-api-key`, cookies, proxy authorization, and routing/account headers; the broker writes its own bearer credential. The broker fixes the Anthropic API version and may grant exact beta header values; other agent beta values fail closed. An operator-owned workspace, project, or organization ID may be supplied by the trusted caller.

Allowed requests are `POST /v1/messages` (including Claude Code's `?beta=true`), `POST /v1/messages/count_tokens`, `GET /v1/models` (optional model discovery), and `POST /v1/responses`. Redirects, compressed responses, unsupported methods and queries, untrusted TLS, and private DNS results fail closed. Responses stream with backpressure and bounded memory. The transport rechecks authorization during the stream and withholds exact echoes of the broker credential, including split-chunk, URL-encoded, JSON-escaped, and base64 forms. A response that echoes a different secret is still native model output and is outside this transport's credential guarantee.

Each request body may be up to 32 MiB. Across active uploads, the transport retains at most 64 MiB of request chunks; the verified listener also limits each session to 32 MiB of those buffers. It returns 503 when either budget is full and releases a reservation after the upstream write finishes or the request ends. Concatenation and TLS writes can briefly use more memory, so this is a request-buffer budget rather than a process-memory ceiling. The Unix listener supplies separate connection and stream limits.

The Unix listener allows four active requests per session by default, configurable from one to eight by the trusted caller, and at most 32 active requests across sessions. Broker approvals and store operations have deadlines and a separate limit of 32 unresolved operations. A timed-out operation keeps its slot until its underlying work settles, so a hung callback can exhaust that budget and fail closed. The peer adapter limits each session to eight sockets and 32 pending verifications. HTTP headers have a 10-second deadline, request bodies a 20-second idle deadline and a 60-second total deadline, and each socket accepts one request. Stopping or expiring a session closes its sockets and active streams. The listener is not exposed on TCP; an agent-local HTTP forwarder would need to live inside a separately enforced agent network boundary.

## Live attachment required

1. Add a durable first-class model-relay approval action scoped to the verified principal, session, provider, fixed route set, API-token handle, optional operator-owned account/workspace ID, and finite lifetime. The in-process approval callback is a fail-closed integration seam, not the durable approval record. Do not treat a copied request ID, process name, bearer, or the current same-UID MCP capability as a principal.
2. Wire the trusted launcher and operator control plane to register sessions and enforce distinct OS identities. The broker must claim the approved action before registering the grant, then use this listener's handle and policy checks. A subprocess with the key in an environment variable is unsafe until agent and broker use distinct OS identities.
3. Expose an agent-local HTTP forwarder only inside that agent's network boundary. It connects to the verified broker Unix socket or Windows named pipe. The relay must not share the operator console's listener or credentials. Windows native peer verification and listener support are still absent.
4. Record route/status/byte counts without logging prompts or credentials. Test two agents simultaneously, including an attempted cross-session connection and Linux PID reuse or passed-FD cases. The current Linux numeric PID/cgroup check is defense in depth, not independent proof.
5. Validate a real Claude Code and Codex turn with tools, retry, token counting, model discovery where enabled, and SSE cancellation. The API-funded gateway is a separate auth and billing path from saved claude.ai or ChatGPT sign-in. Preserve existing sign-in and direct network defaults until an explicit migration is approved.

Claude Code's [gateway compatibility guide](https://code.claude.com/docs/en/llm-gateway-protocol) documents the Messages routes, version and beta headers, response headers, and streaming behavior. The [Claude Platform API overview](https://platform.claude.com/docs/en/api/overview) and [OpenAI Responses reference](https://developers.openai.com/api/reference/resources/responses/methods/create) document the fixed upstream APIs. The OS peer boundary is described in [agent-os-identity.md](agent-os-identity.md).

## Current verification

`npx vitest run tests/model-relay-server.test.ts tests/model-relay-transport.test.ts` uses a synthetic HTTPS provider behind a test-only transport seam. It proves incremental SSE delivery, exact upstream routing, client credential stripping, broker credential substitution, split credential redaction, optional Anthropic routes, OpenAI Responses routing, redirect refusal, authorization refusal, TLS trust failure, and the concurrent request-buffer limit with a full 32 MiB request. The listener test exercises the native Unix peer helper, rejects an unregistered peer, ignores agent-supplied handle headers and queries, enforces the handle policy and approval callback, limits active requests, and closes an active stream on session stop. Its one test peer runs under the test account with only the registration guard mocked; this is not proof of distinct OS isolation or native-agent end-to-end behavior.
