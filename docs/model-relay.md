# Broker-owned model relay

## Status

The streaming transport in `src/model-relay-transport.ts` and Unix HTTP listener in `src/model-relay-server.ts` are opt-in broker APIs. The listener accepts connections only after the native peer helper verifies the Unix socket peer and the broker matches its UID to a registered live session. On Linux it additionally requires the pidfd-backed verifier and fails closed if its helper or the kernel socket option is unavailable. The trusted in-process caller registers one fixed provider and s-gw API-token handle per session for at most 30 minutes. An agent cannot register a session or choose a handle over HTTP. There is no CLI flag, privileged launcher integration, or native-agent routing yet. The current same-UID Anthropic launcher cannot establish the distinct OS identity required to use this listener as a confinement boundary.

The ledger now has a first-class `model_relay` request. A trusted launcher can create it for a verified principal and session; it binds the exact handle, provider, route subset, account IDs, API version, allowed beta values, and lifetime. The operator console or CLI can approve it once. Timed, login-session, and always-allow choices are rejected for this action, and ordinary command execution cannot claim it. Scoped deny and ask policies can name `model_relay`; explicit allow policies are rejected, and preexisting broad allow policies do not autoapprove relay requests. `StoreBackedModelRelayApprovals` claims a request before listener registration and rechecks the persisted request and handle policy for each broker operation. On session end it revokes in-memory authorization first, then writes the terminal ledger state. A failed write emits a nonsecret broker warning or calls the operator's error hook immediately. The adapter retains the end record for an idempotent retry on listener close, and close reports the original failure. If the broker exits before a retry succeeds, the request can remain `executing` until a later store mutation reaps it after the longer of its approved lifetime and the ten-minute stale-execution window. A claim must occur within five minutes of approval. A restarted broker has no active in-memory claim, so old executing requests fail closed. The listener also accepts a custom in-process verifier for tests and integrations; never wire a no-op verifier into an agent-reachable service.

The handle must be an `api-token`, allow `s-gw:model-relay`, and allow the exact `api.anthropic.com:443` or `api.openai.com:443` destination. The listener rechecks approval, store policy, session lifetime, and handle existence during streaming. Registration remains a trusted control-plane API outside the agent boundary. The durable approval is implemented but not attached to a privileged launcher or native agent.

The relay has fixed upstreams: `api.anthropic.com` for Anthropic Messages and `api.openai.com` for OpenAI Responses. It never accepts an upstream URL from an agent, does not implement `CONNECT`, and does not intercept TLS. It drops the client's `Authorization`, `x-api-key`, cookies, proxy authorization, and routing/account headers; the broker writes its own bearer credential. The broker fixes the Anthropic API version and may grant exact beta header values; other agent beta values fail closed. An operator-owned workspace, project, or organization ID may be supplied by the trusted caller. Each grant admits only its approved subset of the fixed provider routes.

Allowed requests are `POST /v1/messages` (including Claude Code's `?beta=true`), `POST /v1/messages/count_tokens`, `GET /v1/models` (optional model discovery), and `POST /v1/responses`. Redirects, compressed responses, unsupported methods and queries, untrusted TLS, and private DNS results fail closed. Responses stream with backpressure and bounded memory. The transport rechecks authorization during the stream and withholds exact echoes of the broker credential, including split-chunk, upper- and lowercase percent-encoded, JSON-escaped, base64, and unpadded base64url forms. Arbitrary transformations of the credential or echoes of a different secret remain outside this transport's guarantee.

Each request body may be up to 32 MiB. A trusted grant can set `maxInputBytes` to a smaller per-request byte limit and `maxOutputTokens` to a per-generation limit. The relay inserts the output limit when it is omitted and rejects a larger or invalid value before contacting the provider. Anthropic `max_tokens: 0` remains valid for cache warming; OpenAI's minimum is 16. Anthropic token-counting requests have no generation limit. Grants without these options keep their existing request bytes. The limits do not cap input tokens or guarantee a cost ceiling.

Across active uploads, the transport retains at most 64 MiB of request chunks; the verified listener also limits each session to 32 MiB of those buffers. It returns 503 when either budget is full and releases a reservation after the upstream write finishes or the request ends. Concatenation and TLS writes can briefly use more memory, so this is a request-buffer budget rather than a process-memory ceiling. The Unix listener supplies separate connection and stream limits.

The Unix listener allows four active requests per session by default, configurable from one to eight by the trusted caller, and at most 32 active requests across sessions. Broker approvals and store operations have deadlines and a separate limit of 32 unresolved operations. A timed-out operation keeps its slot until its underlying work settles, so a hung callback can exhaust that budget and fail closed. The peer adapter limits each session to eight sockets and 32 pending verifications. HTTP headers have a 10-second deadline, request bodies a 20-second idle deadline and a 60-second total deadline, and each socket accepts one request. Stopping or expiring a session closes its sockets and active streams. The listener is not exposed on TCP.

`src/agent-local-model-forwarder.ts` is an opt-in Linux source foundation for a client that needs an HTTP base URL. It copies TCP bytes from `127.0.0.1` inside one agent network namespace to the fixed broker Unix socket; it does not parse authorization headers or select a session from HTTP input. Startup requires a root-owned read-only launch-gate attestation issued after the systemd manager checks the live UID, cgroup, private network namespace, and broker socket. It checks those facts again before accepting each connection. It refuses same-UID, host-network, writable proof, altered socket, and unsupported-platform starts. The root-owned socket handoff is required for a broker socket whose parent is root-controlled. There is no installed forwarder process, native model-client routing, or real two-UID acceptance yet. The synthetic byte-bridge tests use a same-UID TCP server only inside the test harness; they do not establish a confinement boundary.

## Live attachment required

1. Wire the trusted launcher and operator control plane to create the durable request, register sessions, and enforce distinct OS identities. The broker must claim the approved action before registering the grant, then use this listener's handle and policy checks. Do not treat a copied request ID, process name, bearer, or the current same-UID MCP capability as a principal. A subprocess with the key in an environment variable is unsafe until agent and broker use distinct OS identities.
2. Stage and start the Linux agent-local forwarder only after the launch gate and socket handoff attest that agent's UID and private network namespace. Configure the native client with its `http://127.0.0.1:<port>` address. Windows still needs a named-pipe bridge and native acceptance; macOS needs an equivalent supported network boundary before a loopback listener can be used. The relay must not share the operator console's listener or credentials.
3. Record route/status/byte counts without logging prompts or credentials. Test two agents simultaneously, including an attempted cross-session connection and Linux PID reuse or passed-FD cases. The current Linux numeric PID/cgroup check is defense in depth, not independent proof.
4. Validate a real Claude Code and Codex turn with tools, retry, token counting, model discovery where enabled, and SSE cancellation. The API-funded gateway is a separate auth and billing path from saved claude.ai or ChatGPT sign-in. Preserve existing sign-in and direct network defaults until an explicit migration is approved.

Claude Code's [gateway compatibility guide](https://code.claude.com/docs/en/llm-gateway-protocol) documents the Messages routes, version and beta headers, response headers, and streaming behavior. The [Claude Platform API overview](https://platform.claude.com/docs/en/api/overview) and [OpenAI Responses reference](https://developers.openai.com/api/reference/resources/responses/methods/create) document the fixed upstream APIs. The OS peer boundary is described in [agent-os-identity.md](agent-os-identity.md).

## Current verification

`npx vitest run tests/model-relay-server.test.ts tests/model-relay-transport.test.ts` uses a synthetic HTTPS provider behind a test-only transport seam. It proves incremental SSE delivery, exact upstream routing, client credential stripping, broker credential substitution, split credential redaction, optional Anthropic routes, OpenAI Responses routing, redirect refusal, authorization refusal, TLS trust failure, grant byte and output-token limits, and the concurrent request-buffer limit with a full 32 MiB request. The listener test exercises the native Unix peer helper, rejects an unregistered peer, ignores agent-supplied handle headers and queries, enforces the handle policy and approval callback, limits active requests, and closes an active stream on session stop. It also checks durable approval after a store reopen, rejection of forged principal objects and cross-session claims, refusal of reusable approval, route-subset enforcement, policy deny and handle deletion, and finite expiry. Its one test peer runs under the test account with only the registration guard mocked; this is not proof of distinct OS isolation or native-agent end-to-end behavior.
