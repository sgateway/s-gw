# Ubuntu 26.04 root-managed Anthropic launch design

Status: design with fail-closed product registration and forwarder staging slices, 2026-11-12. The opt-in installer can stage an inactive forwarder unit, a preassembled root, a pinned network namespace, and durable forwarder identity receipts. It does not launch the forwarder or release a managed agent. No production launcher, AppArmor override, or live-store change is made by this note. The proposed first supported profile is a separate, root-installed Linux backend for the existing `s-gw run AGENT --sandbox anthropic` command. It must not become the default or claim full compatibility until the gates below pass.

## Why the current launch stops

The pinned `@anthropic-ai/sandbox-runtime` 0.0.50 emits an outer `bwrap` command and then runs `apply-seccomp` inside it. The helper first tries `unshare(CLONE_NEWPID | CLONE_NEWNS)`. Without `CAP_SYS_ADMIN`, it creates another user namespace, writes `/proc/self/setgroups`, `/proc/self/uid_map`, and `/proc/self/gid_map`, and retries. The hosted Ubuntu 26.04 path reaches a denied map write before the agent starts. The local helper patch only skips an already-denied `setgroups` write; it still needs a usable UID/GID mapping and mount/PID namespace. It correctly fails closed when either is unavailable.

Ubuntu's bwrap AppArmor profile allows bwrap to set up a user namespace, then restricts the application inside it, including capability use. Ubuntu documents that this also affects privileged bwrap invocations. The helper cannot grant itself `CAP_SYS_ADMIN`, and replacing its binary cannot make a denied namespace or map operation succeed. A `--cap-add CAP_SYS_ADMIN` string is not a fix when the LSM denies that capability; granting it to the whole bwrap shell/socat phase would also move a powerful capability into the untrusted launch path. Do not turn off AppArmor's user namespace restriction, make bwrap setuid, or set a host-wide permissive userns sysctl to recover this command.

The standalone helper probe and the inside-bwrap probe are diagnostic only. An inside-bwrap pass still does not establish that the exact generated `s-gw run` wrapper and its broker/proxy setup work. `anthropicSandboxReadiness()` checks dependencies, while `--probe-launch` checks only that a no-op starts. The integrated test in `scripts/test-anthropic-seccomp-integrated-linux.mjs` is the first command-level availability check; it is not a production confinement proof.

## Proposed process layout

Keep the current CLI and `anthropicSandboxConfig()` option parsing as the policy input. Add a managed Linux backend behind an explicit operator-selected installation/profile. The operator CLI submits a bounded, versioned launch request to the installed broker. The broker authenticates the operator, resolves policy and paths, then calls root control through the existing kernel-verified control channel. Root control accepts only that registered broker, seals the command, arguments, workspace mounts, option values, and identity generation in a root-owned plan, and launches the following system units behind a closed gate. Neither an agent nor an ordinary same-UID CLI connection may call root control directly.

| Component | Identity and namespace | Authority |
| --- | --- | --- |
| Root control | Root, outside all agent namespaces | Stage/attest units, mounts, static UID leases, socket bindings, and lifecycle. No credentials or approvals. |
| Broker and Anthropic host proxy | Dedicated broker UID, host network namespace | Own store, policy, approved HTTPS/SSH/model TLS, and the pinned runtime's HTTP/SOCKS allowlist proxy. No agent-writable code or configuration. |
| Session forwarder | Dedicated forwarder UID, same private network namespace as its agent, separate PID/cgroup and mount view | Listen on fixed loopback ports; connect only to the session's mounted MCP, model, HTTP-proxy, and SOCKS-proxy Unix sockets. No store, credential, generic URL, or arbitrary Unix-path API. |
| Agent | Fresh dedicated agent UID/GID, private PID/network/IPC/mount views | Run the requested native client or command, using loopback forwarder ports and a scoped workspace. No host socket mount, host network interface, broker store, or capability. |

Use the existing root-owned runtime verifier, root-control channel, durable UID/generation records, launch gate, activated broker sockets, verified MCP/model listeners, per-message Linux gate, and agent-local model forwarder as foundations. A new broker-side registration must bind the **forwarder UID/cgroup** to exactly one agent identity generation and session. The current peer listeners authorize the agent UID/cgroup, so simply running today's forwarder under another UID would fail. Root control attests the forwarder and agent units, the broker socket in the forwarder's private root, and their common network namespace before that registration becomes usable. The broker rejects a copied socket path, client-supplied session ID, forwarded credential claim, and a forwarder from any other cgroup. Root control must attest that the forwarder is outside the agent PID namespace and that both units die and revoke together.

The root manager creates and pins one route-free private network namespace in a root-owned location. Both units use `NetworkNamespacePath=` to join that exact namespace. Do not use `JoinsNamespaceOf=` here: when both units enable `PrivateIPC=` or `PrivateTmp=`, it can join those namespaces too. The staged unit files also set `PrivateNetwork=yes`, but systemd 259 makes that setting ineffective when `NetworkNamespacePath=` is present. The live namespace inode and interface/route inventory are the evidence. Today's helper checks fresh root creation, loopback-only interfaces, and routes exposed by `/proc/net/route` and `/proc/net/ipv6_route`; those files alone do not prove that arbitrary policy-routing tables and rules are empty. Before activation, audit all tables and rules through rtnetlink or retain and verify the root-creation invariant with no privileged mutation path. The root manager must start the forwarder and verify its loopback listeners before releasing the agent gate. Give only the agent unit `PrivatePIDs=yes` so it cannot see or signal the forwarder; verify that the installed systemd supports it and that it actually took effect. Each unit gets its own `PrivateIPC=yes`, `PrivateTmp=yes`, `TemporaryFileSystem=/dev/shm`, `MountFlags=private`, `BindLogSockets=no`, and separate root-owned `RootDirectory=`, plus `ProtectHome=yes`, `ProtectSystem=strict`, `NoNewPrivileges=yes`, empty capability sets, `RestrictNamespaces=yes`, `SystemCallArchitectures=native`, and `KillMode=control-group`. Only the agent gets `ReadWritePaths=` for the staged workspace. `PrivateIPC` does not isolate Unix sockets: filesystem sockets follow the mount view, while abstract sockets follow the network namespace. Validate the *live* UID, cgroup, network/PID/IPC/mount namespace inodes, mount table and propagation fields, route inventory, capability sets, seccomp state, and socket inode before gate release; a unit-file readback alone is insufficient. `systemd` creates namespaces as the trusted system manager before dropping to the agent UID. This path does not execute `bwrap` or create a nested unprivileged user namespace.

The pinned runtime can supply host-side HTTP/SOCKS proxy components, but the current `SandboxManager` is process-global. After the first initialization, a second call returns the first proxy and its host policy; a later stricter session could inherit the earlier allowlist. A local synthetic loopback reproduction confirmed this with a permissive first session and a strict second session. Run one isolated proxy process per session with a pinned config and broker-private `TMPDIR`, or implement an equivalent per-session proxy. The managed backend uses `allowedDomains` derived from `anthropicSandboxConfig()` and never calls `wrapWithSandbox()` on Ubuntu 26.04. It must omit the current same-UID sandbox broker's localhost-port exception and must not pass `SGW_SANDBOX_BROKER_TOKEN` to the agent. The forwarder maps its fixed local HTTP/SOCKS ports to that session's exact broker-private bridges.

The default SRT runtime proxy checks the requested hostname but dials it by name without rejecting private resolved addresses. The opt-in Linux `--pin-public-proxy` path uses a separate per-run HTTP/SOCKS proxy with numeric dialing, but it is not the managed Ubuntu 26 backend. The managed proxy must resolve and pin each destination IP at the dial point, reject loopback, private, link-local, metadata, special-use, and mixed public/private answers by default, and cover both HTTP and SOCKS parent routes. An operator-approved private service needs a separate owned action and explicit destination policy; a compatibility lane that permits transparent private-host access requires Barry's specific approval. Test DNS rebinding by changing answers between requests and verify that the proxy connects only to a previously validated IP for that connection. Permitted HTTPS still uses `CONNECT` without certificate substitution or TLS decryption. The broker-owned model relay is an explicit local HTTP gateway to fixed provider endpoints. Its credential handle, strict payload profile, and provider routes still require an operator-approved grant. The forwarder must be unable to select a new upstream or bypass the proxy.

`src/managed-proxy-dial.ts` supplies numeric dialing to the opt-in Linux `--pin-public-proxy` path and has synthetic tests for restricted and mixed DNS answers. It accepts cancellation and limits underlying work to 16 DNS lookups and 32 connection attempts per process, retaining a slot until a cancelled operation actually settles. Node's `dns.lookup()` cannot be cancelled here, so a stuck lookup can consume a slot and later requests fail closed at capacity. The eventual proxy must separately limit established sockets. The opt-in proxy rejects parent proxy configuration rather than forwarding through an unpinned route. It is not connected to the managed Ubuntu 26 backend; default Linux `--allow-host` behavior is unchanged.

Native Codex and Claude MCP clients use a root-owned stdio bridge staged inside the agent root. It forwards their MCP stdin/stdout bytes over loopback TCP to one fixed port in the session forwarder. The forwarder opens only that session's mounted broker MCP Unix socket and copies bytes without accepting a destination or session selector from the agent. It caps concurrent streams and bytes, closes both sides on error or gate revocation, and never exposes a raw broker token. The broker authenticates the forwarder's kernel UID, cgroup, and live root registration on every message, then attributes the request to the bound agent identity generation. Agents in another private network namespace cannot reach this port. The existing Unix-socket MCP injection cannot simply be reused under an agent-side AF_UNIX filter; native-client compatibility requires this bridge and its installed-host tests.

`native/linux-managed-mcp-stdio/bridge.c` is the uninstalled agent-side transport component. It connects only to IPv4 loopback port `43871` in its private network namespace. It takes no arguments and reads no route configuration from the environment or MCP frames. Like the existing `s-gw-mcp-peer-bridge`, it copies opaque stdio bytes; the broker's MCP parser owns framing. Its bounded 64 KiB buffers and 64 MiB limit per direction cap one connection without imposing a smaller message limit than the pinned MCP SDK's 10 MiB read buffer. I/O errors and a 35-minute idle period close the connection. Broker EOF ends the stdio bridge, while stdin EOF half-closes TCP after queued bytes drain. The root manager must build and stage the binary in a verified root-owned runtime and verify that the fixed port belongs to the attested forwarder before releasing the agent. The new `src/linux-managed-mcp-forwarder.ts` remains a source-only TCP-to-Unix primitive bound to fixed port `43871`. The synthetic socket test runs an SDK MCP handshake through the bridge and, on Linux, runs the bridge under the pinned AF_UNIX-denying filter; it does not establish the separate-UID installed boundary.

The product broker now has an optional, root-provisioned `mcpForwarder` registration path. It assigns the activated MCP socket to a separate forwarder group and asks root control for the peer identity before registration. Root control reads the live systemd unit and process UID/GID, supplementary groups, cgroup, invocation, PID/network/IPC/mount namespaces, durable agent generation, pinned network namespace, and broker socket device/inode. It creates the binding proof itself, sends only the verified forwarder peer to the broker, and repeats the full proof before releasing the agent gate. The broker's existing pidfd and per-message Linux gate then applies to the forwarder UID/cgroup while the principal remains the agent generation. Broker-supplied proof cannot authorize the binding.

**This opt-in path cannot activate yet.** The native root collector deliberately rejects registration because it cannot prove that the agent root has no other broker-socket alias or inherited connected descriptor. Checking only `/run/s-gw/broker.sock` would be insufficient. A staging slice now renders and verifies the inactive forwarder service, declares read-only broker socket and proof mounts into a separately assembled root, pins a fresh loopback-only network namespace with a root native helper, and retains root-private UID/GID/session identity receipts under `/var/lib/s-gw/forwarder-identities`. The agent's opt-in unit joins that namespace with a private PID view, omits direct broker/model socket mounts and environment variables, and assigns its MCP socket to the forwarder group. Its legacy unit path is unchanged. The installer requires a preassembled forwarder root with exact, root-owned Node, entry, and ES module package copies under `/opt/s-gw/forwarder`; it verifies their contents against the trusted host runtime and checks the ELF interpreter and recursive `DT_NEEDED` libraries at their loader-visible paths, modes, and hashes. Executable files stay outside `/run` because systemd mounts an empty `/run` in this chroot when `MountAPIVFS=yes`. The installer does not assemble the root filesystem. Keep `/var/lib/s-gw/forwarder-roots` root-private at `0700` and each individual chroot root root-owned at `0755` so the dedicated UID can traverse `/` after `chroot`. The disposable Ubuntu 26.04 CI fixture stages that bounded library closure, runs an inert transient Node/ESM probe as the forwarder UID in the pinned namespace, reads back the inactive product unit, and verifies that `PENDING` refuses activation. The probe tests load-time dependencies; libraries opened later with `dlopen()` and the product forwarder's `/proc` view remain future runtime gates. The forwarder unit stays inactive, and root control does not yet start it or prove its fixed listener. The stdio bridge, agent-side AF_UNIX filter loader, complete no-direct-socket root audit, model forwarding, and command-level managed backend are still missing. Unit readback and synthetic collector tests are development checks, not an installed confinement result. Do not treat staging as activation-ready.

The runnable-root check supports Linux ELF64 x86_64 and AArch64 only. The root installer uses fixed root-owned `readelf` and `ldconfig` tools to discover the interpreter and recursive load-time dependencies without executing Node during discovery. It rejects unsupported cache entries, ambiguous libraries, loader search directives, writable paths, symlink escapes, and chroot loader configuration. The transient CI probe runs the same chroot Node with `MountAPIVFS=yes`, imports the checked forwarder entry as an ES module, and reads `/proc/self/ns/net`. It does not start the product forwarder or prove the agent filter, MCP client, or production confinement.

Before replacing the collector refusal, freeze the agent cgroup for a stable root/FD inspection, prove it cannot migrate tasks, enumerate every inherited descriptor and socket alias, and inspect live mount propagation for `shared`, `master`, and `propagate_from` fields. Numeric `stat().ino` of a filesystem socket and `/proc/<pid>/fd` `socket:[ino]` are different inode domains; comparing them cannot establish descriptor identity. Use full-width inode values for any positive proof. The current synthetic collector tests inject a successful `attestAgentIsolation` callback and do not exercise the native refusal. Keep the root gate closed through a hosted installed test of the collector, forwarder listener, bridge, teardown, and stale socket denial.

A standalone native census prototype and a fresh Ubuntu 26.04 CI fixture now exercise a smaller claim: a frozen, single-threaded transient process in a minimal chroot has exactly null stdio, no other descriptors or filesystem sockets, no second process with its dedicated UID, and only explicitly listed nonpropagating mountpoints. It also compares the live working directory and user namespace with the expected root and host. The prototype does not yet attest mount roots, sources, filesystem types, or options. The fixture pins `MountAPIVFS=no` because its static gate needs no `/proc`, `/sys`, `/dev`, or `/run` mounts; this is narrower than the product unit. It injects a socket path and extra regular and connected Unix descriptors to prove refusal. Root control does not call this helper, and the product collector still refuses. The real agent needs a root-observable barrier *after* the launch gate closes inherited FDs and *before* it executes the payload, followed by a census of the product root and its writable workspace. The [kernel cgroup v2 documentation](https://docs.kernel.org/admin-guide/cgroup-v2.html) says frozen tasks can still migrate; root-owned cgroup controls, nondelegation, exact membership checks, and a trusted PID 1/root remain necessary. [`mountinfo`](https://man7.org/linux/man-pages/man5/proc_pid_mountinfo.5.html) supplies the live propagation fields and bind-mount roots; unit properties alone do not prove them.

## Agent-side seccomp, after setup

Stage a small root-owned native `managed-agent-exec` in the trusted runtime tree. Systemd runs it **as the agent UID** after the namespaces, mounts, environment, and forwarder are ready. It checks the sealed launch gate, empty effective/permitted/bounding/ambient capabilities, expected UID/GID/cgroup/namespace, and only standard or explicitly approved inherited descriptors. Then it calls `prctl(PR_SET_NO_NEW_PRIVS, 1)`, installs a verified seccomp-BPF filter with `seccomp(SECCOMP_SET_MODE_FILTER, ...)`, and uses `execve()` for the requested command. Filter failure or an unexpected architecture exits before `execve`.

`vendor/anthropic-seccomp/filter-only-exec.c` is an unused filter installer using the pinned BPF bytes. Its disposable Ubuntu 26.04 test checks payload start, AF_UNIX and io_uring denial, AF_INET creation, no inherited extra descriptor, and real exit status. It does not check a root plan or create a namespace; the managed launcher and gate above remain unimplemented.

The filter returns `EPERM` for `socket(AF_UNIX, ...)`, `io_uring_setup`, `io_uring_enter`, and `io_uring_register`; it rejects alternate syscall ABIs and any architecture-specific socket multiplexor that could create AF_UNIX sockets. Deny namespace creation/entry separately with `RestrictNamespaces=yes`; keep the agent's capabilities empty. Add `RestrictAddressFamilies=AF_INET AF_INET6` and `SystemCallArchitectures=native` as defense in depth, but do not count them alone as proof: systemd says the family filter applies to `socket(2)`, not inherited descriptors, `socketpair(2)`, or all io_uring paths. The private network namespace and FD cleanup are independent egress controls. The agent must still be able to use loopback TCP to the fixed forwarder ports. The forwarder does **not** receive the agent filter because it needs AF_UNIX to reach the broker/proxy sockets.

No root privilege is needed to install this filter after `no_new_privs`; the kernel retains it across `execve()` and children. Its source and compiled BPF bytes must be pinned, reviewed for x86_64 and arm64, and tested on the target kernel. Reusing the pinned helper's Unix/io_uring BPF policy is reasonable; reusing its namespace-creating executable is not. `socketpair()` can create an isolated local pair, but it cannot reach a host service unless a connected descriptor is inherited or transferred. Close unexpected FDs before exec, hide host sockets from the agent mount view, and test descriptor transfer and abstract sockets explicitly.

## CLI contract and rollout boundary

The managed backend must preserve `--cwd`, `--command`, arguments, agent environment sanitation, MCP injection for Claude/Codex, `--allow-host`, `--strict-egress`, `--allow-write`, `--deny-read`, `--deny-agent-auth`, `--isolated-auth`, broker options, signal/exit behavior, and cleanup. Translate path rules into a staged root and bind mounts; deny globs need the same expansion and symlink/hardlink checks as the existing sandbox. No agent-writable input may become a root mount destination or trusted policy. Keep default and existing macOS/Linux launch routes unchanged until the managed route passes parity. Do not silently treat an unsupported option as a no-op.

Saved native login files and subscription sign-in are an open compatibility gate. A dedicated agent UID cannot simply read the operator's home, and copying those credentials into the agent root would defeat the credential boundary. The broker-owned model relay proves an API-key-backed model path with synthetic providers, but does not establish subscription login, billing, all tools, or live provider compatibility. A default switch that removes those working capabilities needs Barry's explicit approval. Until then, make the managed route an opt-in profile and report its supported authentication path clearly; do not claim universal production parity.

## Acceptance gates on an installed Ubuntu 26.04 host

1. Build/package: root-owned runtime and loader pass the existing static verifier; neither agent nor forwarder can modify their binary, plan, proxy socket path, broker store, recovery vault, or socket units. No writable dependency, loader override, inherited FD, or PATH helper runs before confinement.
2. Exact CLI launch: the packed `s-gw run codex --sandbox anthropic --strict-egress --probe-launch ...` starts a payload and returns its real status. A no-op plus native Claude/Codex MCP requests through the stdio/TCP bridge and text turns through the approved fixed model relay pass. Test every promised CLI option and native login mode before claiming parity. Run the existing integrated seccomp test as a control, but add a managed-path test for production.
3. Filter: inside the running payload, `socket(AF_UNIX)`, abstract Unix sockets, `io_uring_setup/enter/register`, alternate-ABI/socketcall attempts, `unshare`, and `setns` fail. An unfiltered host/forwarder positive control succeeds. Verify `/proc/<pid>/status` has `NoNewPrivs: 1`, `Seccomp: 2`, and empty capabilities; attempt a fork/exec child and repeat.
4. Network: host controls can reach IPv4, IPv6, and UDP canaries; each agent cannot reach host loopback, non-loopback IPv4/IPv6, UDP/DNS, metadata IPs, or the other session. A direct `connect`/`sendto` attempt and an HTTP/SOCKS `CONNECT` to an unapproved target fail. Two concurrent sessions with different allowlists cannot use each other's hosts. Exactly allowed public hosts pass through the session's pinned proxy without TLS certificate substitution; public-to-private and mixed-answer DNS rebinding fail at the dial point. Kill the proxy or forwarder during a request and prove fail-closed behavior. Inspect network namespace inode and interface/route inventory, not only command output.
5. IPC and identity: two simultaneous agent/forwarder pairs have distinct UIDs, cgroups, socket inodes, and network namespaces. The agent's MCP stdio bridge uses only its fixed loopback TCP port and cannot choose a broker Unix path. MCP/model requests bind the verified forwarder's UID/cgroup to the root-attested agent generation and session through `SO_PEERCRED` plus per-message `SCM_CREDENTIALS`/`SCM_PIDFD`; copied IDs, cross-agent socket paths, and `SCM_RIGHTS` handoff do not cross the boundary. The agent cannot reach D-Bus, SSH agent, Docker/Podman, operator console, or any broker socket by filesystem or abstract name.
6. Lifecycle: a failed filter/mount/socket/namespace/proxy attestation never releases the gate. Kill the agent, forwarder, broker, and root control in turn; confirm the full cgroups stop, connections close, grants revoke, and UID/generation tombstones prevent premature reuse. Reboot/restart and repeat the stale-FD and socket-rebind checks. New credential actions cannot start after revocation; in-flight actions cancel and drain before the boundary is released. A remote side effect sent before cancellation cannot be undone.
7. Provider and UX: synthetic provider fixtures pass first, followed by a real approved provider/account test of streaming, tool calls, cancellation, terminal I/O, HTTPS/SSH actions, and exact output redaction. Confirm the client sees the provider's authentic TLS certificate on permitted `CONNECT` paths. Record any unsupported sign-in or option as an explicit rollout blocker.

This remains an architecture proposal with fail-closed product registration and forwarder staging slices. The present worktree has source foundations and CI fixtures for managed Linux identity, MCP, model relay, and a route-free namespace helper, but no installed Ubuntu 26.04 managed Anthropic backend, activated forwarder lane, native seccomp loader, or real-provider acceptance. The existing `--sandbox anthropic` path must still be described as failing closed on that host.
