# macOS root policy service source

This is an uninstalled IPC skeleton for the two-UID acceptance plan. A trusted root manager would pass an accepted broker control connection on fd 3, a listening, root-owned `agent-network-policy.sock` on fd 4, and an accepted provider connection from the root-owned `agent-provider-attestation.sock` on fd 5. The service checks the socket paths, ownership, modes, parent chain, and extended ACLs. It checks its own pinned code requirement and the broker, runner, and provider peers using kernel audit tokens and pinned code requirements. The provider peer's live code path must resolve to the same pinned bundle that passed the on-disk checks; a copy at another path is refused. All four requirement strings are empty by default, so this source cannot start as a production service without a signed build and explicit pins.

The signed broker must send one `REGISTER-V1 UID GID SESSION UID GID SESSION` line. Both UIDs must resolve to distinct `_sgwagent_` accounts with matching primary GIDs. The service then accepts at most two signed root runner connections. It parses the runner's repeated `CHECK-V1 UID SESSION` frames and matches them to the registered pair. Broker disconnect closes the runner connections.

The provider hook now checks one prerequisite: an on-disk extension bundle at the compile-time `SGW_POLICY_PROVIDER_PATH` must have a root-owned, nonwritable canonical parent chain. Every directory and file inside the bundle must also be root-owned and nonwritable by other users, with no extended ACL allow entries or symlinks. Its signature must pass the pinned `SGW_POLICY_PROVIDER_REQUIREMENT`, bundle ID, and Team ID; its signed entitlements must include `content-filter-provider-systemextension` and must not enable `get-task-allow`. All four pins default to empty, so an ordinary source build cannot pass this check. An ad-hoc signature is rejected even if it carries the requested entitlement.

For each runner check, the service sends `CHALLENGE-V1` with a fresh random nonce, the checked UID/session, and both registered identities to the signed provider peer on fd 5. It accepts only a matching `ATTEST-V1` reply within 500 ms; stale nonces, changed identities, extra frames, and a closed peer fail closed. This establishes a narrow signed-peer liveness exchange, not network enforcement. The service still has no way to verify that the extension is installed and running, that `NEFilterManager` has an enabled configuration with `filterSockets`, or that the provider drops traffic for the exact registered UIDs and sessions. Those proof fields remain zero, so every check still receives `DENIED-V1`, including a valid signed-peer reply. The readiness predicate also requires current-boot denial probes and proof that denial persists between checks. A signed Network Extension and a privileged manager that can verify those facts, plus installer provisioning and native two-UID acceptance, are still required. The runner's heartbeat alone cannot establish that boundary. Nothing here is wired into the CLI, installed, or a change to existing agent behavior.

The source build and fail-closed tests run through `npx vitest run tests/macos-root-policy.test.ts` on macOS. Apple's [Network Extension entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.networking.networkextension) lists `content-filter-provider-systemextension` for Developer ID content filters. Its [deployment guidance](https://developer.apple.com/documentation/technotes/tn3134-network-extension-provider-deployment) requires a macOS content filter system extension, and [system extension guidance](https://developer.apple.com/documentation/systemextensions/) requires matching Team IDs and notarization for direct distribution. Apple documents [socket filtering](https://developer.apple.com/documentation/networkextension/nefilterproviderconfiguration/filtersockets), [source flow audit tokens](https://developer.apple.com/documentation/networkextension/nefilterflow/sourceprocessaudittoken), and [static code validity checks](https://developer.apple.com/documentation/security/code-signing-services/). These APIs alone do not prove installed enforcement.
