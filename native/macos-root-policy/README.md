# macOS root policy service source

This is an uninstalled IPC skeleton for the two-UID acceptance plan. A trusted root manager would pass an accepted broker control connection on fd 3 and a listening, root-owned `agent-network-policy.sock` on fd 4. The service checks the socket paths, ownership, modes, parent chain, and extended ACLs. It checks its own pinned code requirement and the broker and runner peers using kernel audit tokens and pinned code requirements. All three requirement strings are empty by default, so this source cannot start as a production service without a signed build and explicit pins.

The signed broker must send one `REGISTER-V1 UID GID SESSION UID GID SESSION` line. Both UIDs must resolve to distinct `_sgwagent_` accounts with matching primary GIDs. The service then accepts at most two signed root runner connections. It parses the runner's repeated `CHECK-V1 UID SESSION` frames and matches them to the registered pair. Broker disconnect closes the runner connections.

The provider hook intentionally returns no proof. Every valid check receives `DENIED-V1`, including a registered UID. `READY-V1` requires a signed and enabled socket filter, a live provider, exact UID/session policy, current-boot denial probes, and proof that denial persists between checks. A signed Network Extension and a privileged manager that can verify those facts, plus installer provisioning and native two-UID acceptance, are still required. The runner's existing heartbeat alone cannot establish that boundary. Nothing here is wired into the CLI, installed, or a change to existing agent behavior.

The source build and fail-closed tests run through `npx vitest run tests/macos-root-policy.test.ts` on macOS. Apple documents [socket filtering](https://developer.apple.com/documentation/networkextension/nefilterproviderconfiguration/filtersockets), [source flow audit tokens](https://developer.apple.com/documentation/networkextension/nefilterflow), and [dynamic code requirement checks](https://developer.apple.com/documentation/security/seccodecheckvalidity%28_%3A_%3A_%3A%29). These APIs alone do not prove installed enforcement.
